모든 프로토콜에서 반복해서 나타난 실패를 모았다. 통신이 안 될 때 이 목록을 위에서부터 훑으면 대개 걸린다. 순서는 빈도와 확인 비용으로 정렬했다. 흔하고 확인이 싼 것부터다.

## 1. 종단 저항, 없거나 하나뿐이거나 너무 많거나

| | |
| --- | --- |
| 증상 | 오실로스코프에 계단형 링잉, 간헐 오류, 긴 케이블에서만 실패 |
| 원인 | 종단 누락(반사) 또는 과다(진폭 저하). 중간 노드의 내장 종단을 안 껐다 |
| 확인 | 전원 끄고 A–B(또는 CANH–CANL) 저항 측정. 60 Ω이 나와야 한다 |
| 해석 | 120 Ω이면 하나뿐, 40 Ω이면 3개, 무한대면 없거나 단선, 0이면 단락 |

멀티미터 하나로 30초에 확인되고 실제 문제의 상당수를 잡는다. 오실로스코프를 꺼내기 전에 한다. 상세는 [기초 04편](/posts/04-basics-transmission-line/)과 [CAN 02편](/posts/02-can-physical-dominant-recessive/)에 있다.

## 2. 그라운드를 안 이었다, 또는 그라운드 루프

| | |
| --- | --- |
| 증상 | 모터를 구동하면 깨진다, 콘센트를 바꾸면 달라진다, 50~60 Hz 험 |
| 원인 | 차동이어도 공통모드 범위(±7~12 V)를 넘으면 진다. 두 접지점 전위차 |
| 확인 | GND 도통 확인, 다른 콘센트에 꽂아본다, 모터 전원을 꺼본다 |
| 해결 | 3선 배선(A/B/GND), 한 점 접지, 절연(전원까지) |

"차동이니 GND는 안 이어도 된다" 가 가장 흔한 오해다. 그리고 "콘센트를 바꾸면 달라진다" 는 그라운드 루프의 결정적 증거다. 상세는 [기초 03편](/posts/03-basics-physical-differential/)과 [기초 11편](/posts/11-basics-noise-ground-isolation/)에 있다.

## 3. 보율이나 비트 타이밍 불일치

| | |
| --- | --- |
| 증상 | Framing Error 지속, 글자가 규칙적으로 깨짐, 짧은 버스에서는 되는데 길면 안 됨 |
| 원인 | 보율 설정 오류, 분주 오차, 내부 RC 발진기, CAN의 Prop_Seg 부족 |
| 확인 | `0x55` 반복 전송 후 오실로스코프로 비트 폭 실측 |
| 해결 | 크리스탈 사용, 소수 분주, Prop_Seg 재계산 |

"온도가 오르면 깨진다" 면 내부 RC 발진기다. "짧을 때는 되는데 길면 안 된다" 면 CAN의 Prop_Seg 부족이다. "긴 프레임만 실패" 면 클럭 누적 오차다. 상세는 [시리얼 02편](/posts/02-uart-baud-error-budget/)과 [CAN 05편](/posts/05-can-bit-timing/)에 있다.

## 4. 프레임 설정 불일치 (패리티, 정지 비트, CPOL/CPHA)

| | |
| --- | --- |
| 증상 | 아예 안 됨, 값이 1비트 밀려서 읽힘, 간헐적으로만 실패 |
| 원인 | 8N1과 8E1 불일치, SPI 모드 불일치, 데이터 비트 수 |
| 확인 | 양쪽 설정 문서 대조, 4가지 SPI 모드를 다 시도 |

값이 1비트 시프트되어 보이면 CPHA가 틀린 것이다. 가장 악질은 8E1로 송신하고 8N1로 수신하는 경우다. 패리티 값에 따라 되기도 하고 안 되기도 한다. 상세는 [시리얼 03편](/posts/03-uart-frame-parity-stop/)과 [SPI 06편](/posts/06-spi-modes-cpol-cpha/)에 있다.

## 5. 방향 전환 타이밍 (RS-485 DE)

| | |
| --- | --- |
| 증상 | 마지막 바이트만 안 온다, CRC가 항상 틀림, 저속에서는 되는데 고속에서 깨짐 |
| 원인 | `TXE`(다음 바이트 넣어도 됨)를 `TC`(선로에 다 나감)로 착각 |
| 해결 | DE는 반드시 `TC` 플래그에서 내린다. DMA면 TC 인터럽트에서 |

같은 구조의 문제가 SPI에도 있다. DMA 완료와 전송 완료는 다르므로 BSY 플래그를 확인한 뒤 CS를 올린다. "버퍼가 비었다 ≠ 선로에 나갔다" 를 기억하면 둘 다 잡는다. 상세는 [시리얼 07편](/posts/07-rs485-half-duplex-direction/)과 [SPI 08편](/posts/08-spi-dma-interrupt-cost/)에 있다.

## 6. 오버런, 소프트웨어가 느리다

| | |
| --- | --- |
| 증상 | 대량 전송 중 일부 유실, 잘 되다가 갑자기 완전히 멎음 |
| 원인 | ISR에서 파싱까지 함, 우선순위 낮음, FIFO 미사용, 보율이 처리 능력 초과 |
| 확인 | ORE와 FIFO overrun 카운터. 0이어야 한다 |
| 해결 | ISR은 버퍼에 넣기만, DMA와 링 버퍼, 우선순위 조정 |
| 주의 | ORE를 클리어 안 하면 수신이 영영 멎는다 |

오버런은 통신 문제가 아니라 소프트웨어 문제다. 케이블을 바꿔도 안 없어진다. "잘 되다가 갑자기 안 온다" 의 1순위가 ORE 미클리어다. 상세는 [시리얼 08편](/posts/08-serial-errors-framing-overrun/)과 [시리얼 11편](/posts/11-mcu-uart-driver-ringbuffer-dma/)에 있다.

## 7. 엔디안, 오프셋, 구조체 패딩

| | |
| --- | --- |
| 증상 | 값이 완전히 엉뚱함(`1000` 이 `-402653184` 로), 32비트만 이상, 특정 상대와만 안 맞음 |
| 원인 | 엔디안 반대, Modbus 워드 순서, `struct` 패딩, PDO 매핑 오프셋 |
| 확인 | 16진수로 원본 바이트를 찍어본다, `sizeof` 확인 |
| 해결 | 명시적 직렬화(시프트로 바이트 하나씩), 바이트 나열을 검사하는 테스트 |

필드버스는 little-endian(CANopen, EtherCAT)이고 Modbus는 big-endian이다. 한 시스템에 둘 다 있으면 반드시 헷갈린다. 그리고 Modbus 32비트 값의 워드 순서는 규격에 없어서 벤더마다 4가지 조합이 나온다.

왕복 테스트만 하면 양쪽이 똑같이 틀려도 통과한다. 반드시 정확한 바이트 나열을 검사한다. 상세는 [기초 09편](/posts/09-basics-endian-alignment/)과 [시리얼 09편](/posts/09-modbus-rtu-frame-crc16/)과 [EtherCAT 10편](/posts/10-process-data-pdo-mapping/)에 있다.

## 8. FSM이 안 올라갔다

| | |
| --- | --- |
| 증상 | 통신은 되는데 아무 일도 안 일어난다, 축이 움직이지 않는다 |
| 원인 | NMT가 Pre-op, ESM이 SAFEOP, CiA 402가 Switch on disabled, 폴트 미리셋 |
| 확인 | Statusword, AL Status Code, NMT 상태를 로그에 찍는다 |
| 해결 | FSM마다 전이 조건 확인. 여러 FSM이 겹쳐 있음을 잊지 않는다 |

EtherCAT 로봇에서는 FSM이 셋 겹친다. ESM, CiA 402, 동작 모드다. "OP인데 축이 움직이지 않는다" 의 답이 이것이고, "폴트가 안 풀린다" 는 Fault reset이 상승 엣지이기 때문이다. 상세는 [CAN 13편](/posts/13-cia402-drive-state-machine/)과 [EtherCAT 08편](/posts/08-esm-state-machine/)과 [EtherCAT 12편](/posts/12-coe-cia402-bringup/)에 있다.

## 9. 워치독이 없거나 시간이 틀렸다

| | |
| --- | --- |
| 증상 | 케이블을 뽑았는데 모터가 계속 구동된다. 정상 운전에서는 아무 증상이 없다 |
| 원인 | SM 워치독 미설정, 시간이 너무 길다, 애플리케이션 워치독 없음 |
| 확인 | 케이블 뽑기 테스트를 실제로 한다 |
| 해결 | SM 워치독 설정 + 애플리케이션 타임아웃 + 안전 상태 정의 |

이 항목이 목록에서 가장 위험하다. 나머지는 "안 되는" 문제인데 이건 "되는 것처럼 보이다가 사고가 나는" 문제다. 커미셔닝 체크리스트에 케이블 뽑기 테스트를 반드시 넣는다. 안 하면 절대 발견되지 않는다. 상세는 기초 08편과 [EtherCAT 07편](/posts/07-syncmanager-buffer-mailbox/)에 있다.

## 10. 실시간 경로에 하면 안 되는 것을 넣었다

| | |
| --- | --- |
| 증상 | 사이클 지터, 가끔 주기를 놓침, OP에서 SAFEOP로 떨어짐 |
| 원인 | 제어 루프에서 로깅, 동적 할당, 락, SDO, I²C, 파일 I/O, 소켓 |
| 확인 | GPIO 토글과 오실로스코프, 지터 히스토그램의 최댓값 |
| 해결 | 실시간 경로에서 전부 빼고 3버퍼로 다른 스레드에 넘긴다 |

`printf` 하나가 수백 µs를 소비한다. 디버깅하려고 넣은 로그가 문제를 만드는 전형이다. "가끔 OP에서 SAFEOP로 떨어진다" 면 마스터 지터이고 AL Status Code는 `0x001A` 다. 상세는 [기초 10편](/posts/10-basics-realtime-jitter/)과 [EtherCAT 15편](/posts/15-cycle-jitter-realtime-os/)에 있다.

## 진단의 메타 원칙

이 목록 전체에 걸리는 원칙이 넷이다.

| 원칙 | |
| --- | --- |
| ① 아래층부터 | 전기, 비트, 프레임, 프로토콜, 애플리케이션 순서로 |
| ② 한 번에 하나씩 | 여러 개를 동시에 바꾸면 왜 됐는지 모른다 |
| ③ "언제 깨지나" 를 먼저 묻는다 | 모터? 온도? 케이블을 만지면? 콘센트를 바꾸면? |
| ④ 카운터를 남긴다 | "가끔 이상하다" 를 "포트 3에서 분당 40건" 으로 바꾼다 |

④가 가장 가치 있다. 코드에 진단을 심어두면 계측기 없이도 원인이 좁혀지고 현장에서 재현 못 하는 문제도 로그로 잡힌다.

## 정리

- 10대 패턴: 종단, 그라운드, 보율과 타이밍, 프레임 설정, 방향 전환(TXE와 TC), 오버런, 엔디안과 오프셋, FSM, 워치독, 실시간 경로 오염
- 앞의 둘은 멀티미터 하나로 30초다. 가장 값싸고 잘 듣는다
- 다섯 번째와 여섯 번째는 "버퍼가 비었다 ≠ 선로에 나갔다" 와 "통신이 아니라 소프트웨어" 를 기억하면 잡힌다
- 일곱 번째는 16진수로 원본 바이트를 찍어보면 대개 즉시 보인다
- 아홉 번째(워치독)가 가장 위험하다. 정상 운전에서 증상이 없고 사고가 나야 발견되므로 케이블 뽑기 테스트가 필수다
- 부록 21번(CSP 목표값 미초기화)은 축이 최대 속도로 급이동한다. 시운전 시 부하 분리가 필수다
- 메타 원칙 넷: 아래층부터, 한 번에 하나씩, "언제 깨지나", 카운터를 남긴다
