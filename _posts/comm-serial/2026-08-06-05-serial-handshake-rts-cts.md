## 1. 받는 쪽이 못 따라갈 때

[기초 08편](/posts/08-basics-flow-control/)의 흐름 제어 문제다. 송신자가 계속 보내는데 수신자 버퍼가 차면 오버런이 나고 데이터가 사라진다.

UART 에는 데이터 자체에 흐름 제어 장치가 없다. CAN 의 중재나 I²C 의 클럭 스트레칭 같은 게 없다. 그래서 바깥에서 해결한다. 하드웨어 흐름제어는 별도 신호선인 RTS 와 CTS 로 하고, 소프트웨어 흐름제어는 데이터 흐름 안에 XON 과 XOFF 문자를 끼워 보내고, 상위 계층에서는 Modbus 처럼 요청과 응답 페이스로 한다.

## 2. RTS 의 두 가지 뜻

원래 뜻과 현재 쓰임이 다르다.

| | 원래 (RS-232 모뎀 시대) | 현대 (하드웨어 흐름제어) |
| --- | --- | --- |
| RTS | Request To Send. 내가 보내고 싶다 | Ready To Receive. 나는 받을 수 있다 |
| CTS | Clear To Send. 보내도 좋다는 모뎀의 허가 | 상대가 받을 수 있다 |

TIA/EIA-232-E 가 이 현실을 인정해서 RTS 를 RTR 로 재정의했다. 하지만 핀 이름은 관성으로 RTS 로 남았다.

```mermaid
flowchart LR
  ARTS[장치 A RTS 출력] -->|나 받을 수 있다| BCTS[장치 B CTS 입력]
  BRTS[장치 B RTS 출력] -->|나 받을 수 있다| ACTS[장치 A CTS 입력]
```

규칙은 이렇다. 내 수신 버퍼가 차면 내 RTS 를 비활성으로 만들고, 상대가 CTS 로 보고 송신을 멈춘다. 내 버퍼에 여유가 생기면 RTS 를 활성으로 되돌려 상대가 다시 보내게 한다. 그리고 나는 송신 전에 내 CTS 를 확인한다.

전기적 극성에 주의한다. RS-232 선에서 활성은 양전압인 space, 곧 +12 V 이고 비활성은 음전압이다. 데이터와 극성이 같다. 반면 MCU 핀 레벨에서는 보통 활성이 LOW 다. `nRTS` 와 `nCTS` 로 표기한다. 어느 쪽 이야기인지 항상 확인한다.

## 3. 하드웨어 흐름제어의 반응 속도

RTS 를 내렸다고 즉시 멈추지 않는다. 얼마나 늦게 멈추는지가 버퍼 설계를 정한다.

수신 버퍼가 임계치에 도달해 RTS 를 비활성으로 만들면, 상대 UART 가 CTS 를 확인하는 시점은 다음 바이트를 시작하기 직전이다. 이미 전송을 시작한 바이트는 끝까지 나가고, 상대의 송신 FIFO 에 이미 들어간 바이트가 있으면 그것도 나갈 수 있다.

최악 지연은 1~2 바이트 시간에 상대 FIFO 깊이를 더한 값이다. 115200 8N1 이면 바이트당 86.8 µs 이고 FIFO 가 16 단계면 최악 약 1.5 ms 분량이 더 올 수 있다.

그래서 임계치를 둔다.

```cpp
// comm_serial/flow_control.hpp
// 수신 링 버퍼가 이 정도 차면 RTS 를 내린다.
// 상대 FIFO 깊이와 전송 중 바이트와 여유를 감당할 만큼 남겨야 한다.
struct FlowThresholds {
    std::size_t buffer_size;
    std::size_t high_watermark;   // 이 이상 차면 RTS 비활성
    std::size_t low_watermark;    // 이 이하로 줄면 RTS 활성 (히스테리시스)
};

// 256바이트 버퍼에 상대 FIFO 16, 전송 중 2, 여유를 더해 32바이트를 남긴다
inline constexpr FlowThresholds kUartFlow{
    .buffer_size    = 256,
    .high_watermark = 224,   // 256 - 32
    .low_watermark  = 160,   // 히스테리시스. 바로 다시 켜지 않는다
};
```

히스테리시스가 중요하다. high 와 low 를 같은 값으로 쓰면 버퍼가 임계 근처에서 출렁일 때 RTS 가 초당 수천 번 토글한다. 상대 UART 가 그걸 다 처리하느라 처리량이 떨어진다.

## 4. XON 과 XOFF

데이터 흐름 안에 제어 문자를 끼워 보낸다. XON 은 DC1 이고 `0x11` 로 계속 보내라는 뜻이다. XOFF 는 DC3 이고 `0x13` 으로 멈추라는 뜻이다.

치명적 한계가 있다. 전송하려는 데이터에 `0x11` 이나 `0x13` 이 들어 있으면 수신 측이 그걸 제어 문자로 해석해서 흐름이 멈춘다. 그리고 데이터도 사라진다.

| 데이터 종류 | XON/XOFF |
| --- | --- |
| ASCII 텍스트 (터미널) | 쓸 수 있다. 제어 문자가 나오지 않는다 |
| Modbus RTU | 절대 안 된다. 바이너리다 |
| 엔코더나 센서 값 | 안 된다 |
| 이스케이핑을 직접 구현한 프로토콜 | 가능하지만 복잡도가 는다 |

임베디드 제어에서는 사실상 쓰지 않는다. 존재를 알아둘 뿐이고 실수로 켜져 있으면 재현이 어려운 문제가 되니 오히려 꺼야 할 대상이다.

실제 사례 패턴이 있다. 리눅스에서 시리얼 포트를 열 때 `termios` 를 raw 로 만들지 않으면 `IXON` 과 `IXOFF` 가 기본으로 켜져 있을 수 있다. 그러면 바이너리 데이터 중 `0x11` 과 `0x13` 이 커널에서 가로채여 애플리케이션에 오지 않는다.

반응 속도도 나쁘다. XOFF 는 송신 큐에 들어가 순서를 기다린다. 상대가 긴 데이터를 보내는 중이면 내 XOFF 는 그 뒤에 나간다. 하드웨어 RTS 가 즉시 내려가는 것과 대조적이다.

## 5. 비교표

| | RTS/CTS | XON/XOFF | 없음 (Modbus 방식) |
| --- | --- | --- | --- |
| 추가 선 | 2개 | 0 | 0 |
| 바이너리 데이터 | 가능하다 | 불가능하다 | 가능하다 |
| 반응 속도 | 1~2 바이트로 빠르다 | 큐를 기다린다 | — |
| 구현 복잡도 | 하드웨어가 해준다 | 소프트웨어가 한다 | — |
| RS-485 에서 | RTS 가 방향 전환에 쓰여 못 쓴다 | 못 쓴다 | 쓸 수 있다 |
| 권장 | 점대점 고속 링크 | 임베디드에서는 권하지 않는다 | 요청과 응답 프로토콜 |

RS-485 멀티드롭에서는 흐름 제어가 아예 없다. RTS 는 방향 전환에 쓰이고 XON/XOFF 는 바이너리라 못 쓴다. 그래서 Modbus 같은 요청과 응답 구조가 흐름 제어를 대신한다. 마스터가 응답을 기다리는 동안 아무도 보내지 않으니 넘칠 일이 없다.

## 6. 흐름 제어가 필요한지 먼저 따진다

대부분의 임베디드 시스템은 흐름 제어가 필요 없다.

| 상황 | 흐름 제어 필요 여부 |
| --- | --- |
| Modbus 요청과 응답. 한 번에 최대 256바이트 | 불필요하다. 프로토콜이 페이스를 정한다 |
| 로그를 흘려보내기만 한다 | 잃어도 되면 불필요하다 |
| 대량 데이터 전송. 펌웨어 업데이트나 파형 덤프 | 필요하다 |
| 호스트 PC 가 느릴 수 있다. USB-시리얼이나 OS 스케줄링 | 필요하다 |
| 수신 버퍼가 64바이트 미만인데 고속이다 | 필요하다 |

흐름 제어 대신 쓸 수 있는 것도 있다. 버퍼를 키우는 게 가장 단순하고, 최악 폭주량에 안전계수를 곱해 잡는다. DMA 와 큰 링 버퍼를 쓰면 CPU 개입 없이 받아둘 수 있다. 프로토콜 레벨에서 블록마다 ACK 을 요구하는 방법도 있고 펌웨어 업데이트에서 흔하다. 보율을 낮추는 것은 확실하지만 느리다.

실무 순서는 버퍼 키우기, DMA, 그래도 안 되면 RTS/CTS 다. 흐름 제어는 선과 복잡도를 추가하니 마지막 수단이다.

## 7. 진단

| 증상 | 원인 후보 |
| --- | --- |
| 대량 전송 중 일부가 사라진다 | 오버런이다. 흐름 제어가 없거나 버퍼가 부족하다 |
| 통신이 갑자기 멈추고 돌아오지 않는다 | XOFF 를 받고 XON 을 못 받았거나 RTS 가 내려간 채 안 올라온다 |
| 바이너리 전송에서만 멈춘다 | XON/XOFF 가 켜져 있다. 데이터에 `0x13` 이 있었다 |
| RTS/CTS 를 켰는데 아무것도 안 온다 | 케이블에 7번과 8번 선이 없거나 널모뎀에서 안 꼬았다 |
| RTS 가 초당 수천 번 토글한다 | 히스테리시스가 없다 |
| RS-485 에서 흐름 제어를 켰더니 깨진다 | RTS 가 방향 전환과 충돌한다 |

통신이 멈췄을 때는 RTS 와 CTS 선의 전압을 재본다. 한쪽이 계속 비활성이면 그쪽 버퍼가 안 비워지고 있다는 뜻이고, 그건 수신 소프트웨어가 멈췄다는 신호다.

## 정리

- UART 에는 내장 흐름 제어가 없어서 바깥에서 해결한다.
- RTS 의 뜻이 바뀌었다. 원래 보내고 싶다였지만 현대 관례는 나는 받을 수 있다다. TIA-232-E 가 공식 인정했다.
- 전기적 극성에 주의한다. RS-232 선에서 활성은 양전압이고 MCU 핀에서는 보통 활성이 LOW 다.
- RTS 반응은 즉시가 아니다. 최악 1~2 바이트에 상대 FIFO 깊이를 더한 만큼 여유를 남기고 임계치를 잡는다.
- 임계치에 히스테리시스를 둔다. 안 그러면 RTS 가 폭주 토글한다.
- XON/XOFF 는 바이너리 데이터에 쓸 수 없다. 임베디드에서는 꺼야 할 대상이다.
- 리눅스에서 `termios` 를 raw 로 안 만들면 `IXON` 이 켜져 있어 바이너리가 커널에서 가로채인다.
- RS-485 멀티드롭에는 흐름 제어가 없다. 요청과 응답 프로토콜이 페이스를 정한다.
- 실무 순서는 버퍼 키우기, DMA, 마지막에 RTS/CTS 다.
