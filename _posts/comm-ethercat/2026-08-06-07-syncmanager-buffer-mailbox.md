## 1. 문제, 두 주인이 같은 메모리를 본다

02편에서 예고한 부작용이다. ESC는 프레임에서 받은 값을 DPRAM에 µs 단위로 쓰고, MCU는 제어 주기마다 그 자리를 읽는다.

ESC가 쓰는 그 순간에 MCU가 읽고 있으면 32비트 위치 값의 앞 2바이트는 새 값, 뒤 2바이트는 옛 값이 된다. 찢어진 값(torn read)이다. [기초 09편](/posts/09-basics-endian-alignment/)에서 본 문제이고 모터 명령으로 들어가면 위험하다.

SyncManager가 이 접근을 하드웨어로 조정한다.

## 2. SyncManager의 역할

각 ESC는 SM을 여러 개(대개 4~8개) 갖는다. 하나가 DPRAM의 한 구간을 담당한다.

| SM | 관례적 용도 | 모드 |
| --- | --- | --- |
| SM0 | 메일박스 출력 (마스터에서 슬레이브로) | 메일박스 |
| SM1 | 메일박스 입력 (슬레이브에서 마스터로) | 메일박스 |
| SM2 | 프로세스 데이터 출력 (RxPDO) | 버퍼 |
| SM3 | 프로세스 데이터 입력 (TxPDO) | 버퍼 |

메일박스를 안 쓰는 단순 슬레이브(디지털 I/O 등)는 SM0과 SM1이 없고 그 번호가 프로세스 데이터가 되기도 한다. 배치는 슬레이브마다 다르니 ESI 파일이나 데이터시트를 본다.

설정 항목은 물리 시작 주소, 길이, 모드(버퍼 또는 메일박스), 방향, 워치독 활성, 인터럽트다.

## 3. 버퍼 모드, 프로세스 데이터용

[기초 08편](/posts/08-basics-flow-control/)에서 소프트웨어로 만든 3버퍼를 하드웨어가 그대로 한다. 같은 크기 버퍼 3개를 두고 하나는 읽는 중, 하나는 최신 완성본, 하나는 쓰는 중으로 돌린다.

| 상황 | 결과 |
| --- | --- |
| ESC가 프레임에서 새 값을 받는다 | 비어 있는 버퍼에 쓰고 완료되면 최신으로 표시 |
| MCU가 읽는다 | 항상 최신 완성본을 읽는다 |
| 둘이 동시에 접근 | 서로 다른 버퍼라 충돌이 없다 |
| MCU가 읽는 동안 새 값이 두 번 왔다 | 중간 값은 버려지고 최신만 남는다 |

핵심 성질이 셋이다. 찢어진 값이 절대 안 나오고, 아무도 안 기다리고, 낡은 값이 버려진다.

[SPI 07편](/posts/07-spi-multislave-cs-daisy/)의 데이지 체인, 기초 08편의 `LatestValue`, EtherCAT SM 버퍼 모드가 전부 같은 구조다. 규모와 구현(소프트웨어 또는 하드웨어)만 다르다.

### 데이터 유실이 정상이다

MCU가 느리면 중간 프레임의 값을 못 본다. 이건 결함이 아니라 설계다. 1 kHz로 프레임이 오는데 MCU가 500 Hz로 읽으면 절반을 놓친다. 제어 데이터는 상태이므로 최신만 의미 있다.

다만 놓치고 있다는 사실은 알아야 한다. 그래서 슬레이브 펌웨어에 프레임 수신 카운터를 두고 자기 처리 횟수와 비교한다.

## 4. 메일박스 모드, 비주기 데이터용

SDO 같은 파라미터 접근은 최신값이 아니라 하나도 빠뜨리면 안 되는 데이터다. [CAN 12편](/posts/12-canopen-sdo-pdo/)의 SDO와 PDO 분리와 같은 이유다.

버퍼 하나에 핸드셰이크를 붙인 구조다.

| 상황 | 결과 |
| --- | --- |
| 마스터가 쓴다 (SM0) | 버퍼가 꽉 찬 상태가 된다 |
| MCU가 읽는다 | 버퍼가 비워진다 |
| MCU가 읽기 전에 마스터가 또 쓰면 | 거부된다. WKC가 안 오른다 |

WKC가 안 오르는 것이 흐름 제어 신호가 된다. 마스터는 WKC를 보고 "아직 안 읽었구나" 를 알고 재시도한다. 기초 08편의 흐름 제어가 여기서는 WKC 기반으로 구현된다. I²C의 클럭 스트레칭, RS-232의 RTS/CTS와 같은 목적을 다른 방법으로 이룬다.

### 마스터 쪽에서 보이는 모습

```cpp
// SOEM 의 SDO 는 내부적으로 메일박스를 쓴다
int size = sizeof(std::uint16_t);
std::uint16_t statusword{};
const int wkc = ec_SDOread(slave, 0x6041, 0x00, FALSE,
                           &size, &statusword, EC_TIMEOUTRXM);
if (wkc <= 0) {
    // 메일박스가 안 비었거나, 슬레이브가 응답 안 함, 또는 타임아웃
    ++stats_.sdo_failures;
}
```

SDO는 여러 프레임에 걸쳐 진행된다. 요청을 메일박스에 쓰고 슬레이브가 처리하고 응답을 메일박스에서 읽는다. 수 사이클이 걸릴 수 있다.

그래서 제어 루프 안에서 SDO를 호출하면 안 된다. CAN 12편의 결론과 같다. 설정은 부팅 때 하고 운전 중에는 PDO만 쓴다.

## 5. SM 워치독, 안전의 핵심

기초 08편에서 워치독이 안전의 핵심이라고 했다. EtherCAT는 그걸 슬레이브 하드웨어에 넣었다.

정상일 때는 프레임이 주기적으로 와서 워치독 타이머가 리셋된다. 케이블이 빠지거나 마스터가 죽어서 정해진 시간(예: 100 ms) 동안 프로세스 데이터가 안 오면 슬레이브가 스스로 SAFEOP로 내려가고 출력을 안전값으로 만든다.

| 워치독 | 감시 대상 |
| --- | --- |
| SM 워치독 | 프로세스 데이터 출력(SM2)에 쓰기가 오는가 |
| PDI 워치독 | MCU가 ESC에 접근하는가 (슬레이브 펌웨어 감시) |

판단이 슬레이브 쪽에 있다는 게 결정적이다. 마스터가 정지해도, 케이블이 빠져도 슬레이브가 스스로 멈춘다. 마스터의 감시에 의존하지 않는다. 이게 없으면 케이블이 빠졌을 때 모터가 마지막 명령대로 계속 구동된다.

### 워치독 시간 설정

| 고려 | |
| --- | --- |
| 너무 짧으면 | 일시적 지터에 오탐이 나서 불필요한 정지 |
| 너무 길면 | 고장 감지가 늦다 |
| 관례 | 제어 주기의 10~100배 |

1 ms 사이클이면 워치독 100 ms 정도다. 그런데 100 ms 동안 모터가 얼마나 움직이는가. 1 m/s로 가면 10 cm다. 안전 요구에 따라 이게 충분한지 계산해야 한다.

부족하면 워치독을 줄이는 게 아니라 별도의 안전 계층(FSoE 등)이 필요하다. 워치독은 통신 감시이지 안전 기능이 아니다. [기초 07편](/posts/07-basics-error-detection/)의 "CRC는 기능안전을 대신하지 못한다" 와 같은 이야기다.

### 설정 확인

```cpp
// SOEM 에서 워치독 시간 설정 (레지스터 직접 접근)
// 0x0400: Watchdog Divider, 0x0420: SM Watchdog
void set_sm_watchdog_ms(int slave, std::uint32_t ms) {
    // 분주기 기준 시간 × 카운트 = 워치독 시간 (ESC 데이터시트 참조)
    const std::uint16_t divider = 2498;   // 기본값 → 100 µs 단위
    const std::uint16_t counts  = static_cast<std::uint16_t>(ms * 10);
    ec_FPWR(ec_slave[slave].configadr, 0x0400,
            sizeof(divider), &divider, EC_TIMEOUTRET);
    ec_FPWR(ec_slave[slave].configadr, 0x0420,
            sizeof(counts),  &counts,  EC_TIMEOUTRET);
}
```

레지스터 값과 시간의 관계는 ESC 칩마다 다르다. 데이터시트를 확인하고 설정 후 실제로 케이블을 뽑아서 몇 ms 만에 정지하는지 측정한다. 계산만 믿지 않는다.

이 테스트는 반드시 한다. 워치독이 설정되지 않았거나 시간이 틀렸는데 그걸 모른 채 운영하는 게 가장 위험하다.

## 6. SM 설정은 누가 하나

| 방법 | 언제 |
| --- | --- |
| ESI 파일 기반 자동 | 대부분. 마스터가 ESI를 읽고 설정 |
| SDO로 동적 설정 | PDO 매핑을 바꿀 때. SM 크기도 따라 바뀐다 |
| 수동(레지스터 직접) | 특수한 경우, 디버깅 |

```cpp
ec_config_init(FALSE);
// (PDO 매핑을 바꾸려면 여기서 PREOP 상태로 SDO 를 쓴다 — 10편)
ec_config_map(io_map.data());   // SM + FMMU 설정
```

PDO 매핑을 바꾸면 SM 크기가 바뀐다. 순서가 중요하다. PREOP에서 PDO 매핑을 하고, SM 크기를 갱신하고, FMMU를 설정한 뒤 SAFEOP로 간다. 08편의 상태 전이가 이 순서를 강제한다.

## 7. 진단

| 증상 | 원인 |
| --- | --- |
| SAFEOP에서 OP로 전이 실패 | SM 설정 오류가 가장 흔하다. AL Status Code 확인 |
| 프로세스 데이터 크기가 안 맞는다 | SM 길이와 PDO 매핑 크기가 다르다 |
| SDO가 가끔 실패 | 메일박스가 안 비었다. 재시도 간격을 본다 |
| 케이블을 뽑았는데 모터가 계속 구동된다 | 워치독이 꺼져 있거나 시간이 너무 길다 |
| 값이 가끔 튄다 | SM이 버퍼 모드가 아닌가. 드물지만 설정 오류 가능 |

네 번째가 가장 위험하고, 테스트를 안 하면 절대 발견되지 않는다. 정상 운전에서는 아무 증상이 없기 때문이다. 커미셔닝 체크리스트에 케이블 뽑기 테스트를 반드시 넣는다.

## 정리

- ESC와 MCU가 같은 DPRAM을 보기 때문에 찢어진 값이 나올 수 있다
- SyncManager가 하드웨어로 조정한다. 관례는 SM0/1이 메일박스, SM2/3이 프로세스 데이터다
- 버퍼 모드(3버퍼)는 프로세스 데이터용이다. 찢어진 값이 없고 아무도 안 기다리고 낡은 값은 버려진다
- 기초 08편의 `LatestValue`, SPI 07편의 데이지 체인과 같은 구조다
- 데이터 유실이 정상이다. 최신만 의미 있기 때문이다
- 메일박스 모드(1버퍼 + 핸드셰이크)는 SDO 등 비주기용이다. 읽기 전에 또 쓰면 거부되고 WKC가 안 오르는 것이 흐름 제어 신호다
- 제어 루프 안에서 SDO를 호출하지 않는다. 수 사이클이 걸린다
- SM 워치독이 안전의 핵심이다. 프로세스 데이터가 안 오면 슬레이브가 스스로 SAFEOP로 내려간다
- 판단이 슬레이브 쪽에 있어서 마스터가 정지해도 동작한다
- 관례는 제어 주기의 10~100배다. 그 시간 동안 로봇이 움직이는 거리를 계산한다
- 부족하면 워치독을 줄이는 게 아니라 별도 안전 계층(FSoE)이 필요하다
- 케이블 뽑기 테스트를 커미셔닝 체크리스트에 반드시 넣는다. 정상 운전에서는 증상이 안 보인다
