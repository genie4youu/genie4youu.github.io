## 1. Classic CAN 의 두 한계

Classic CAN 은 30년을 잘 버텼지만 두 가지가 걸림돌이 됐다.

| 한계 | 왜 문제인가 |
| --- | --- |
| 데이터 8바이트 | 32비트 위치에 32비트 속도면 8바이트다. 한 축의 상태 하나로 꽉 찬다. 진단과 상태 비트를 넣을 자리가 없다 |
| 최대 1 Mbps | 중재의 왕복 요구가 물리적 상한을 만든다 |

CAN FD 는 이 둘을 중재와 데이터를 분리해서 푼다.

## 2. 한 프레임 안에서 속도를 바꾼다

```mermaid
flowchart LR
  A[중재 구간 500 kbps] -->|BRS 에서 전환| B[데이터 구간 2~8 Mbps]
  B -->|다시 원래 속도| C[후반 중재 구간 500 kbps]
```

중재 구간에는 SOF 와 ID 와 RTR/RRS 와 IDE 와 FDF 가 들어가고, 데이터 구간에는 BRS 이후의 ESI 와 DLC 와 데이터와 CRC 가 들어가고, 후반 구간에는 CRC delimiter 와 ACK 와 EOF 가 들어간다.

중재를 빠르게 하지 못하는 이유는 [03편](/posts/03-can-arbitration/)의 제약 그대로다. 중재 중에는 버스의 모든 노드가 같은 비트를 같은 시점에 보고 판단해야 한다. 신호가 버스를 왕복할 시간이 한 비트 안에 들어가야 한다.

$$\text{Prop Seg} \geq 2 \times (t_{\text{케이블}} + t_{\text{트랜시버}})$$

데이터 구간에는 이게 필요 없다. 송신자 한 명만 말하고 있으니 남의 반응을 기다릴 이유가 없다. 수신자는 그냥 받기만 하면 된다.

왕복이 필요한 구간과 편도면 되는 구간을 분리했다는 이 한 문장이 CAN FD 의 전부다. 이 발상은 EtherCAT 의 on-the-fly 처리와도 통한다. 그쪽도 왕복을 없애는 방향으로 문제를 푼다.

## 3. 바뀐 것들

| 항목 | Classic CAN | CAN FD |
| --- | --- | --- |
| 데이터 길이 | 0~8 바이트 | 0~64 바이트 |
| 데이터 구간 속도 | 중재와 같다 | 최대 8 Mbps 다. 트랜시버와 버스에 따라 다르다 |
| CRC | 15비트 | 데이터 16바이트 이하면 17비트, 넘으면 21비트 |
| Remote Frame | 있다 | 삭제됐다 |
| 스터프 비트 카운터 | 없다 | 추가됐다 |
| 오류 상태 표시 | 없다 | ESI 비트로 송신자가 Error Passive 인지 알린다 |
| 새 비트 | — | FDF(FD 프레임 표시), BRS(속도 전환), ESI |

Classic 에서 전부 8 이던 DLC 9~15 를 재활용했다.

| DLC | Classic | CAN FD |
| --- | --- | --- |
| 0~8 | 0~8 | 0~8 |
| 9 | 8 | 12 |
| 10 | 8 | 16 |
| 11 | 8 | 20 |
| 12 | 8 | 24 |
| 13 | 8 | 32 |
| 14 | 8 | 48 |
| 15 | 8 | 64 |

길이가 연속이 아니다. 20바이트를 보내려면 24바이트 DLC 를 쓰고 4바이트를 패딩해야 한다. 직렬화 코드에서 이걸 처리해야 한다.

```cpp
// comm_can/can_fd.hpp
// 필요한 바이트 수를 담을 수 있는 가장 작은 FD 길이로 올린다
constexpr std::uint8_t fd_round_up(std::uint8_t n) {
    constexpr std::uint8_t kLens[] = {0,1,2,3,4,5,6,7,8,12,16,20,24,32,48,64};
    for (auto l : kLens) if (l >= n) return l;
    return 64;   // 초과는 호출자가 검사해야 한다
}
static_assert(fd_round_up(9)  == 12);
static_assert(fd_round_up(20) == 20);
static_assert(fd_round_up(21) == 24);
```

## 4. 얼마나 좋아지나

32바이트 데이터를 보낸다고 하자. Classic CAN 을 500 kbps 로 쓰면 8바이트씩 4개 프레임으로 쪼개야 한다.

$$4 \times 135\ \text{비트} = 540\ \text{비트} \times 2\ \mu s = 1080\ \mu s$$

CAN FD 로 중재를 500 kbps, 데이터를 2 Mbps 로 하면 한 프레임에 담긴다.

| 구간 | 비트 | 시간 |
| --- | --- | --- |
| 중재 구간 약 20비트를 500 kbps 로 | 20 | 40 µs |
| 데이터 구간 약 300비트를 2 Mbps 로 | 300 | 150 µs |
| 후반 중재 구간 약 15비트를 500 kbps 로 | 15 | 30 µs |
| 합계 | | 약 220 µs |

1080 µs 가 220 µs 로 약 5배 빨라진다. 그리고 프레임이 하나라 중재 오버헤드가 1/4 로 준다. 데이터가 클수록 이득이 커진다. 8바이트 하나만 보낼 때는 이득이 별로 없다. 중재 구간 오버헤드가 그대로이기 때문이다.

## 5. CRC 계산 방식이 바뀐 이유

CAN FD 는 CRC 를 그냥 늘린 게 아니라 계산 방식을 바꿨다.

| | Classic | CAN FD |
| --- | --- | --- |
| 스터프 비트 | CRC 계산에서 제외한다 | 포함한다 |
| 추가 필드 | 없다 | 스터프 비트 카운터 3비트에 패리티 1비트를 더했다 |

Classic CAN 에서 특정 오류가 스터프 비트의 개수를 바꿔버리면 수신자가 비트열을 다르게 해석하면서도 CRC 는 우연히 맞을 수 있는 시나리오가 알려져 있었다.

CAN FD 는 두 가지로 막는다. 스터프 비트를 CRC 대상에 포함시켜 스터핑 결과가 달라지면 CRC 가 달라지게 했고, 스터프 비트 개수를 프레임에 명시해 개수가 안 맞으면 즉시 검출되게 했다. [07편](/posts/07-can-error-detection/)에서 본 여러 겹으로 겹친다는 원칙의 연장이다. 하나의 검사에 빈틈이 발견되면 다른 각도의 검사를 추가한다.

## 6. 실무 함정

### 트랜시버 지연 보상

데이터 구간이 빨라지면 새 문제가 생긴다. MCU 가 비트를 내면 트랜시버 송신 지연으로 예를 들어 120 ns 뒤에 버스에 나가고, 트랜시버 수신 지연으로 다시 120 ns 뒤에 MCU 가 되읽는다. Bit Error 검사용이다. 왕복 지연이 240 ns 다.

데이터 구간이 5 Mbps 면 한 비트가 200 ns 다. 왕복 지연 240 ns 가 한 비트보다 길다. 되읽기 시점이 이미 다음 비트로 넘어가 있어서 정상인데도 Bit Error 로 판정한다.

TDC(Transmitter Delay Compensation)가 이걸 고친다. 컨트롤러가 실제 지연을 측정해서 되읽기 시점을 그만큼 뒤로 미룬다. 데이터 구간이 약 1 Mbps 를 넘으면 TDC 설정이 필수다. 안 하면 고속에서만 Bit Error 가 쏟아진다. 컨트롤러 설정에서 TDC 항목을 반드시 확인한다.

### Classic 노드와 섞으면 안 된다

| 트랜시버와 컨트롤러 등급 | 의미 |
| --- | --- |
| CAN FD capable | FD 프레임을 보내고 받는다 |
| CAN FD tolerant | FD 프레임을 이해하지는 못해도 오류로 취급하지 않고 무시한다 |
| Classic only | FD 프레임을 오류로 판정하고 Error Frame 을 쏜다 |

Classic 전용 노드가 하나라도 있으면 FD 프레임을 쓸 수 없다. 그 노드가 FD 프레임마다 Error Frame 을 날려 버스를 마비시킨다. 혼용하려면 모든 노드가 최소한 FD tolerant 여야 한다. 부품 선정 단계에서 확인한다.

### 거리가 짧아진다

데이터 구간이 빠르면 신호 품질 요구가 올라간다. 종단과 스터브와 케이블 품질이 Classic 보다 훨씬 중요해진다.

| 데이터 속도 | 실용적 버스 길이 (대략) |
| --- | --- |
| 2 Mbps | 수십 m |
| 5 Mbps | 10~20 m |
| 8 Mbps | 수 m |

중재 속도는 그대로여도 데이터 속도가 거리를 제한한다. 두 개의 제약을 동시에 만족해야 한다.

## 7. CAN FD 를 쓸까 말까

| 상황 | 판단 |
| --- | --- |
| 8바이트로 충분하고 대역폭도 여유가 있다 | Classic 으로 충분하다. FD 는 복잡도만 는다 |
| 데이터가 8바이트를 자주 넘는다 | FD 를 쓴다 |
| 대역폭이 빠듯하다 | FD 를 쓴다 |
| 기존 Classic 장비와 섞어야 한다 | tolerant 여부를 확인한다 |
| µs 급 다축 동기가 필요하다 | FD 로도 안 된다. EtherCAT 로 간다 |

CAN FD 가 EtherCAT 를 대체하지는 않는다. 대역폭은 늘었지만 분산 클록이 없다. 다축이 같은 순간에 반응해야 하는 문제는 여전히 풀지 못한다. FD 의 자리는 Classic CAN 이 대역폭 때문에 아깝게 안 되던 경우다.

## 정리

- CAN FD 는 Classic 의 두 한계인 8바이트와 1 Mbps 를 중재와 데이터를 분리해서 푼다.
- 중재 구간은 왕복이 필요해 느리고, 데이터 구간은 편도라 빠르게 할 수 있다.
- 바뀐 것은 64바이트와 데이터 구간 최대 8 Mbps 와 CRC 17/21비트와 Remote Frame 삭제와 ESI 비트다.
- DLC 가 재정의됐고 길이가 연속이 아니다. 패딩 처리가 필요하다.
- 32바이트 전송이 Classic 4프레임 1080 µs 에서 FD 1프레임 약 220 µs 로 5배 빨라진다.
- CRC 계산 방식이 바뀐 이유는 스터프 비트 개수가 바뀌는 시나리오의 취약점 때문이다. 스터프 비트를 CRC 에 포함하고 카운터를 추가했다.
- TDC 는 데이터 1 Mbps 이상에서 필수다. 안 하면 고속에서만 Bit Error 가 쏟아진다.
- Classic 전용 노드가 하나라도 있으면 FD 프레임을 못 쓴다. 최소 FD tolerant 가 필요하다.
- 데이터 속도가 거리를 제한한다. 5 Mbps 면 10~20 m 다.
- FD 는 EtherCAT 를 대체하지 않는다. 분산 클록이 없어 µs 급 다축 동기는 여전히 불가능하다.
