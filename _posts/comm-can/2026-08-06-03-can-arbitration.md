## 1. 여럿이 동시에 말하기 시작했다

버스에 노드가 10개 있고 그중 셋이 정확히 같은 순간에 송신을 시작했다면 어떻게 되는가.

| 프로토콜 | 답 |
| --- | --- |
| RS-485 | 충돌한다. 프로토콜 규율로 애초에 못 하게 막는다 |
| 이더넷 (CSMA/CD) | 셋 다 버리고 무작위 시간 뒤 재시도한다 |
| CAN | 한 명이 이기고 그 프레임은 1비트도 늦지 않는다 |

## 2. 원리는 쓰면서 동시에 읽는 것이다

CAN 노드는 송신 중에 자기가 쓴 값과 버스의 실제 값을 매 비트마다 비교한다. 내가 recessive 인 1 을 냈는데 버스가 dominant 인 0 이면 다른 누군가가 더 높은 우선순위를 보내고 있다는 뜻이다. 나는 진 것이니 즉시 조용해지고 수신 모드로 전환한다.

[02편](/posts/02-can-physical-dominant-recessive/)의 와이어드 AND 가 이걸 가능하게 한다. dominant 를 낸 쪽이 항상 버스를 지배하므로 진 쪽만 자기가 졌다는 걸 알고 이긴 쪽은 아무것도 모른 채 계속 진행한다.

세 노드가 동시에 시작했다고 하자. 표준 11비트 ID 를 비교한다.

| | ID (16진) | ID (2진, MSB 먼저) |
| --- | --- | --- |
| 노드 A | `0x123` | `001 0010 0011` |
| 노드 B | `0x121` | `001 0010 0001` |
| 노드 C | `0x200` | `010 0000 0000` |

CAN 은 ID 의 MSB 부터 보낸다.

| 비트 # | A | B | C | 버스 (AND) | 결과 |
| --- | --- | --- | --- | --- | --- |
| 10 | 0 | 0 | 0 | 0 | 전원 계속 |
| 9 | 0 | 0 | 1 | 0 | C 탈락. 1 을 냈는데 0 이 읽혔다 |
| 8 | 1 | 1 | — | 1 | 계속 |
| 7 | 0 | 0 | — | 0 | 계속 |
| 6 | 0 | 0 | — | 0 | 계속 |
| 5 | 1 | 1 | — | 1 | 계속 |
| 4 | 0 | 0 | — | 0 | 계속 |
| 3 | 0 | 0 | — | 0 | 계속 |
| 2 | 0 | 0 | — | 0 | 계속 |
| 1 | 1 | 0 | — | 0 | A 탈락 |
| 0 | — | 1 | — | 1 | B 승리 |

B 의 `0x121` 이 이겼다. ID 값이 가장 작다. 0 이 dominant 라서 작은 값이 이긴다는 규칙이 성립한다. 만약 1 이 dominant 였다면 큰 값이 이겼을 것이다. 우연이 아니라 설계다.

B 의 프레임은 중재 때문에 단 1비트도 지연되지 않았다. B 는 자기가 경쟁했다는 사실도 모른다. A 와 C 는 버스가 비면 자동으로 재시도하고 하드웨어가 처리한다. 버스 낭비가 0 이다. 이더넷은 충돌할 때마다 프레임 두 개 분량을 버리지만 CAN 은 경쟁이 프레임 전송의 일부로 흡수된다.

## 3. 왜 이게 실시간 제어에 결정적인가

[기초 10편](/posts/10-basics-realtime-jitter/)에서 실시간의 정의는 최악의 경우를 계산할 수 있는가였다.

| | 이더넷 CSMA/CD | CAN 중재 |
| --- | --- | --- |
| 충돌 해결 | 무작위 백오프 | 결정적이다. ID 로 확정된다 |
| 최악 지연 | 확률적이라 상한이 없다 | 계산할 수 있다 |
| 급한 메시지 | 다른 것과 똑같이 대기한다 | ID 를 낮추면 먼저 간다 |

ID 를 낮추면 먼저 간다는 게 설계 도구가 된다. 안전 신호에 `0x000` 대역을, 상태 방송에 `0x700` 대역을 주면 우선순위가 시스템 설계에 명시적으로 표현된다.

대가도 있다. 높은 우선순위 메시지가 버스를 가득 채우면 낮은 우선순위는 영원히 못 보낼 수 있다. starvation 이라 부른다. 방어는 버스 부하율을 30~50% 이하로 유지하고, 고주기 메시지에 너무 낮은 ID 를 주지 않고, 낮은 우선순위 메시지의 송신 대기 시간을 감시해 임계를 넘으면 경고하는 것이다.

## 4. 중재가 거리를 제한한다

[02편](/posts/02-can-physical-dominant-recessive/)에서 예고한 것의 정확한 이유다. 중재가 성립하려면 버스의 모든 노드가 같은 비트를 같은 시점에 보고 판단해야 한다. 노드 A 가 낸 dominant 가 버스 반대편 노드 Z 의 샘플링 시점 전에 도착해야 하고 Z 의 반응도 A 에게 돌아와야 한다.

$$\text{Prop Seg} \geq 2 \times \left(t_{\text{케이블}} + t_{\text{트랜시버 out}} + t_{\text{트랜시버 in}}\right)$$

1 Mbps 로 계산하면 이렇다.

| 항목 | 시간 |
| --- | --- |
| 비트 시간 | 1000 ns |
| 케이블 40 m 편도 (5 ns/m) | 200 ns |
| 트랜시버 지연 (송신과 수신, 편도) | 약 100 ns |
| 편도 합계 | 300 ns |
| 왕복 | 600 ns |
| 남는 것 (동기와 위상 세그먼트) | 400 ns |

빠듯하다. 이래서 1 Mbps 에서 40 m 가 상한이다. 중재를 포기하면 이 제약이 사라진다. 그게 CAN FD 의 아이디어다. 데이터 구간에는 중재가 없으니 왕복을 기다리지 않아도 되고 그래서 8 Mbps 까지 올릴 수 있다.

## 5. 중재 구간에서는 Bit Error 판정이 다르다

[07편](/posts/07-can-error-detection/)에서 볼 Bit Error, 곧 내가 쓴 값과 읽은 값이 다른 것은 오류다. 그런데 중재 구간에서는 오류가 아니다.

| 구간 | 내가 1 을 냈는데 0 이 읽히면 |
| --- | --- |
| 중재 필드 (ID) | 정상이다. 중재에서 진 것이다 |
| ACK 슬롯 | 정상이다. 다른 노드가 ACK 을 낸 것이다 |
| 그 외 (데이터, CRC 등) | Bit Error 다 |

같은 전기적 현상이 구간에 따라 중재 패배이기도 하고 오류이기도 하다. CAN 컨트롤러가 지금 어느 필드를 보내는 중인지 알고 있어야 판정이 된다. 문맥에 따라 같은 입력의 의미가 달라지는 이런 구조가 FSM 설계의 전형이다. Stateflow 로 CAN 프로토콜 엔진을 그려보면 이 부분이 계층 State 로 자연스럽게 표현된다.

## 6. ID 배정은 시스템의 우선순위 정책이다

| 원칙 | 이유 |
| --- | --- |
| 급하고 짧은 주기에 낮은 ID 를 준다 | 최악 지연이 작아야 한다 |
| 안전 관련은 최상위로 둔다 | E-stop 상태와 폴트 방송이다 |
| 긴 주기와 비주기는 높은 ID 로 둔다 | 진단과 설정이다 |
| ID 중복을 금지한다 | 두 노드가 같은 ID 를 보내면 중재로 구분되지 않는다 |

ID 중복이 치명적인 이유가 있다. 두 노드가 같은 ID 로 다른 데이터를 동시에 보내면 ID 구간에서는 값이 같으니 둘 다 이긴다. 그런데 데이터 필드에서 값이 갈리는 순간 recessive 를 낸 쪽이 Bit Error 를 검출한다. 오류 프레임이 나가고 재전송하고 또 충돌하는 일이 무한 반복된다. 결과적으로 두 노드 모두 오류 카운터가 올라가 Bus Off 로 가고 버스가 사실상 멎는다.

그래서 ID 배정표는 시스템 설계 문서의 필수 항목이다. 노드를 추가할 때마다 확인한다.

| ID 대역 | 용도 |
| --- | --- |
| `0x000`~`0x00F` | 안전과 긴급. E-stop 과 치명 폴트다 |
| `0x080`~`0x0FF` | 동기 신호. CANopen SYNC 는 `0x080` 이다 |
| `0x100`~`0x2FF` | 고주기 제어 데이터인 위치와 속도와 토크다 |
| `0x300`~`0x4FF` | 중주기 상태다 |
| `0x500`~`0x6FF` | 설정과 파라미터. CANopen SDO 다 |
| `0x700`~`0x7FF` | 진단과 하트비트다 |

CANopen 은 이 배정을 표준으로 정해뒀다. predefined connection set 이라 부르고 직접 설계할 필요가 없어진다.

## 7. 우선순위를 코드로 표현하기

ID 를 매직 넘버로 흩뿌리면 나중에 우선순위를 볼 수 없다. 한 곳에 모아 정렬 가능하게 만든다.

```cpp
// comm_can/message_ids.hpp
// 이 파일이 곧 시스템의 우선순위 정책 문서다.
// 값이 작을수록 급하다. 순서대로 정렬해서 유지한다.
#pragma once
#include <cstdint>

namespace ids {
// 안전이 최우선이다
inline constexpr std::uint32_t kEmergencyStop    = 0x001;
inline constexpr std::uint32_t kSafetyFault      = 0x002;

// 동기
inline constexpr std::uint32_t kSync             = 0x080;

// 고주기 제어. 1 kHz 다
inline constexpr std::uint32_t kAxisCmdBase      = 0x100;   // 축 번호를 더한다
inline constexpr std::uint32_t kAxisFeedbackBase = 0x180;

// 중주기 상태. 100 Hz 다
inline constexpr std::uint32_t kSystemState      = 0x300;

// 설정과 진단은 비주기다
inline constexpr std::uint32_t kSdoRequestBase   = 0x600;   // 노드 번호를 더한다
inline constexpr std::uint32_t kHeartbeatBase    = 0x700;
} // namespace ids

// 컴파일 타임에 중복을 잡는다. 축이 늘어도 겹치지 않는지 확인한다
static_assert(ids::kAxisCmdBase + 5 < ids::kAxisFeedbackBase,
              "축 명령 ID 대역이 피드백 대역과 겹친다");
static_assert(ids::kAxisFeedbackBase + 5 < ids::kSystemState,
              "축 피드백 ID 대역이 상태 대역과 겹친다");
```

`static_assert` 로 대역 겹침을 컴파일 타임에 잡는다. 축이 6개에서 8개로 늘 때 조용히 겹치는 사고를 막는다. [시리얼 02편](/posts/02-uart-baud-error-budget/)의 보율 `static_assert` 와 같은 발상이다.

## 정리

- 원리는 송신하면서 동시에 읽는 것이다. recessive 를 냈는데 dominant 가 읽히면 진 것이다.
- 작은 ID 가 이긴다. 0 이 dominant 이기 때문이고 우연이 아니라 설계다.
- 비파괴라 이긴 프레임은 1비트도 늦지 않고 자기가 경쟁했다는 것도 모른다. 버스 낭비가 0 이다.
- 이더넷 CSMA/CD 는 충돌 시 둘 다 버려 최악 지연 상한이 없지만 CAN 은 계산할 수 있다.
- ID 배정이 곧 우선순위 정책이라 설계 도구가 된다.
- 대가는 낮은 우선순위가 굶을 수 있다는 것이다. 버스 부하율을 30~50% 로 유지하고 대기 시간을 감시한다.
- 중재가 왕복을 요구해서 거리가 제한된다. 1 Mbps 에서 왕복 600 ns 라 40 m 가 한계다.
- CAN FD 는 데이터 구간에 중재가 없어서 빠르게 할 수 있다.
- 중재 구간과 ACK 슬롯에서는 쓴 값과 읽은 값이 달라도 오류가 아니다. 문맥에 따라 의미가 달라진다.
- ID 중복은 치명적이다. 두 노드가 같은 ID 로 다른 데이터를 보내면 무한 재전송으로 양쪽 다 Bus Off 가 된다.
- ID 를 한 파일에 모으고 `static_assert` 로 대역 겹침을 컴파일 타임에 잡는다.
