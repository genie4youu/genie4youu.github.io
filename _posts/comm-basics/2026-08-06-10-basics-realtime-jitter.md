## 1. 빠르다는 잘못된 목표다

통신 사양서를 보면 속도부터 나온다. 1 Mbps, 100 Mbps 같은 숫자다. 그런데 제어 루프가 실제로 요구하는 건 이게 아니다. 이 값이 언제 측정됐고 언제 도착하며 그 시간이 매번 같은가를 묻는다.

| 용어 | 정의 | 제어에서 의미 |
| --- | --- | --- |
| 처리량 | 초당 몇 비트 | 대개 관심 없다. 제어 데이터는 작다 |
| 지연 | 측정에서 도착까지 걸린 시간 | 위상 여유를 갉아먹는다. 일정하면 보상할 수 있다 |
| 지터 | 그 지연이 얼마나 흔들리나 | 보상이 불가능하다 |

결정성은 최악의 경우가 얼마인지 계산 가능한가를 말한다. 평균이 아니라 상한이 있는 것이 실시간의 정의다.

## 2. 지연이 제어를 망가뜨리는 방식

순수 시간 지연 $\tau$ 의 주파수 응답은 이렇다.

$$G_{\text{delay}}(j\omega) = e^{-j\omega\tau}$$

크기는 1 이라 신호를 줄이지 않는다. 위상만 $-\omega\tau$ 라디안 늦춘다. 교차 주파수(제어 대역폭) $\omega_c$ 에서의 위상 손실은 이렇게 나온다.

$$\Delta\phi = -\omega_c \tau \ \text{[rad]} = -\frac{180}{\pi}\,\omega_c\tau \ \text{[deg]}$$

| 제어 대역폭 $\omega_c$ | 총 지연 $\tau$ | 위상 손실 | 판단 |
| --- | --- | --- | --- |
| 50 rad/s (약 8 Hz) | 1 ms | 2.9° | 무시 가능 |
| 50 rad/s | 5 ms | 14.3° | 눈에 띈다 |
| 200 rad/s (약 32 Hz) | 1 ms | 11.5° | 눈에 띈다 |
| 200 rad/s | 5 ms | 57° | 위상 여유가 통째로 날아간다 |
| 500 rad/s (약 80 Hz) | 2 ms | 57° | 같은 상황 |

일반적으로 위상 여유는 45~60° 를 목표로 잡는다. 지연이 그중 20° 이상을 먹으면 설계가 무너진다. 경험칙으로 정리하면 이렇다.

$$\omega_c \cdot \tau \lesssim 0.3\ \text{rad} \quad\Rightarrow\quad \tau \lesssim \frac{0.3}{\omega_c}$$

이게 ADRC 에서 본 대역폭을 막는 벽 중 하나다. 관측기 대역폭 $\omega_o$ 를 아무리 올리고 싶어도 루프 지연이 상한을 정한다. 통신 선택이 곧 제어 성능의 상한을 정한다는 뜻이다. 대역폭 200 rad/s 를 원하면 총 지연 예산이 1.5 ms 이고, 그 안에 센서와 통신과 연산과 구동이 다 들어가야 한다.

### 지연 예산은 통신만이 아니다

| 구간 | 전형값 |
| --- | --- |
| 엔코더 측정 | 50 µs |
| 엔코더 전송 | 20 µs |
| MCU 연산 | 200 µs |
| 필드버스 | 250 µs |
| 드라이브 | 50 µs |
| PWM 갱신 (ZOH, $T_s/2$) | 500 µs |
| 합계 | 약 1.07 ms |

샘플링 자체가 지연이다. 영차 홀드는 평균 $T_s/2$ 의 지연을 만든다. 1 kHz 면 500 µs 이고 위 예산에서 가장 큰 항목이다. 통신을 µs 단위로 다듬어도 샘플 주기가 크면 소용없다.

## 3. 지터가 지연보다 나쁜 이유

일정한 지연은 설계에 넣을 수 있다. 모델에 $e^{-j\omega\tau}$ 를 넣고 예측 보상을 붙이고 대역폭을 그만큼 낮추면 된다. 알고 있으면 다룰 수 있다. 지터는 매번 다르니 모델에 넣을 수 없다.

### 지터가 미분 추정을 망가뜨린다

속도를 위치 차분으로 추정한다고 하자.

$$\hat v = \frac{x_k - x_{k-1}}{T_s}$$

코드는 공칭 $T_s$ = 1 ms 를 쓴다. 그런데 실제 샘플 간격이 지터로 $1\,\text{ms} \pm 50\,\mu s$ 라면 이렇게 된다.

$$\hat v = \frac{\Delta x}{T_s^{\text{공칭}}} = \frac{v \cdot T_s^{\text{실제}}}{T_s^{\text{공칭}}} = v \cdot \frac{1.05\ \text{또는}\ 0.95}{1.0}$$

속도 추정에 ±5% 오차가 매 주기 무작위로 들어간다. 5% 지터가 5% 속도 노이즈가 된다. 이게 D 항이나 ESO 를 통해 증폭돼 가청 소음과 진동으로 나타난다. 관절이 100 rad/s 로 돌면 추정 속도가 ±5 rad/s 로 튀고, 미분 이득이 붙으면 토크 명령이 요동친다.

곧 지터는 조금 늦는 것이 아니라 센서 노이즈가 늘어난 것처럼 작용한다. 그리고 노이즈는 대역폭 상한을 직접 내린다.

부분적 대응이 있다. 실제 경과 시간을 타임스탬프로 재서 $\Delta t$ 를 실측값으로 쓰면 이 오차는 사라진다. EtherCAT DC 가 주는 게 정확히 이것이다. 모든 슬레이브가 같은 시각을 공유하니 언제 샘플링했는가가 확정된다. 다만 구동 쪽 지터는 이걸로도 고치지 못한다. 토크 명령이 언제 실제로 반영되는지가 흔들리면 방법이 없다.

### 재는 것은 평균이 아니라 최악이다

평균 220 µs 는 의미 없는 숫자다. 최악 2.4 ms 가 한 번이라도 나오면 제어 루프는 그 주기를 놓친다. 실시간 시스템의 사양은 항상 최댓값으로 쓴다. 지연 히스토그램을 뜨면 본체는 200~260 µs 에 몰려 있고 꼬리 하나가 2.4 ms 에 서 있는 모양이 나오는데, 시스템을 결정하는 건 그 꼬리다.

리눅스에서는 `cyclictest -m -p 99 -i 1000 -l 3600000` 으로 이 히스토그램을 직접 뜰 수 있다.

## 4. 지터는 어디서 생기나

| 원천 | 전형 크기 | 대응 |
| --- | --- | --- |
| OS 스케줄링 | 일반 리눅스 수 ms, PREEMPT_RT 수십 µs | RT 커널, `SCHED_FIFO`, CPU 격리(`isolcpus`) |
| 인터럽트 지연 | µs 에서 수백 µs | 우선순위 조정, ISR 을 짧게, 인터럽트 비활성 구간 최소화 |
| 버스 중재 | CAN 은 최악이 상위 우선순위 메시지들의 합 | 우선순위 설계, 부하율 관리 |
| 재전송 | 프레임 1개 시간 곱하기 재시도 횟수 | one-shot 모드, 주기 전송으로 대체 |
| 버퍼링 | USB-시리얼 latency timer 기본 16 ms | 타이머를 1~2 ms 로 낮추거나 USB 를 제어 경로에서 뺀다 |
| 스위치 큐잉 | store-and-forward 는 프레임 하나 시간에 큐 대기 | 제어망에 일반 스위치를 넣지 않는다 |
| 캐시와 DMA 경합 | µs 단위 | 코드와 데이터 배치, TCM 사용 |
| 동적 메모리와 락 | 예측 불가 | 실시간 경로에서 `new`, `malloc`, `mutex` 금지 |

제어 경로에서 USB 를 빼라는 말이 나오는 이유가 표에 있다. USB-시리얼 어댑터의 기본 latency timer 16 ms 는 제어 관점에서 재앙이다. 디버깅과 로깅에는 좋지만 루프 안에 넣으면 안 된다.

## 5. 프로토콜은 결정성을 어떻게 확보하나

```mermaid
flowchart LR
  A[아무것도 안 함] --> B[우선순위]
  B --> C[폴링]
  C --> D[시간 슬롯 스케줄]
  D --> E[스케줄 + 공통 시각]
```

| 방식 | 어떻게 | 쓰는 곳 | 결과 |
| --- | --- | --- | --- |
| 아무것도 안 함 | 먼저 온 게 먼저 | 표준 이더넷, UART | 상한이 없다 |
| 우선순위 | 급한 메시지가 이긴다 | CAN 중재 | 상위 메시지만 준보장. 하위는 굶을 수 있다 |
| 폴링 | 마스터가 순서대로 물어본다 | Modbus, I²C | 계산은 되지만 느리다 |
| 스케줄 | 시간 슬롯을 미리 배정한다 | TDMA, EtherCAT, TSN | 상한이 설계로 확정된다 |
| 스케줄과 공통 시각 | 모든 노드가 같은 시계를 본다 | EtherCAT DC, IEEE 1588 | 동시 동작까지 보장된다 |

마지막 줄이 중요하다. 스케줄만으로는 데이터가 제때 도착한다까지다. 그런데 다관절 로봇은 여러 축이 같은 순간에 움직여야 한다. 축 1이 5 µs 먼저 반응하고 축 3이 5 µs 늦으면 궤적이 틀어진다.

그래서 EtherCAT 는 분산 클록으로 모든 슬레이브의 시계를 맞춘다. 데이터가 조금 일찍 도착하든 늦게 도착하든 정해진 시각에 동시에 반영한다. 공개 자료가 밝히는 동기 정확도는 1 µs 이하다. 이게 빠른 통신과 실시간 통신의 차이다. 1 Gbps 이더넷보다 100 Mbps EtherCAT 가 제어에 좋은 이유는 속도가 아니라 이것이다.

## 6. 숫자로 보는 비교

| 프로토콜 | 전형 사이클 | 지터 | 상한 계산 |
| --- | --- | --- | --- |
| Modbus RTU (10 노드) | 35 ms | 크다 | 폴링 순서로 계산 가능 |
| CAN 500 kbps | 1~10 ms | 우선순위에 따라 다르다 | 우선순위별로 계산 가능 |
| 표준 이더넷과 TCP | 수 ms | 수십 ms 까지 | 불가 |
| 표준 이더넷과 UDP (전용망) | 1 ms 미만 | 수백 µs | 부하가 낮으면 가능 |
| EtherCAT | 0.1~1 ms | 1 µs 미만 (DC) | 설계로 확정 |
| SPI (점대점) | µs | ns 급 | 마스터가 전부 결정 |

SPI 가 지터 면에서는 최고다. 마스터가 클럭을 직접 주니 모호함이 없다. 그래서 조인트 내부의 엔코더 읽기는 지금도 SPI 계열이 표준이다. 문제는 거리와 노드 수뿐이다.

## 7. 설계할 때 실제로 하는 일

1. 제어 대역폭 $\omega_c$ 를 먼저 정한다. 지연 예산 $\tau \lesssim 0.3/\omega_c$ 가 나온다.
2. 예산을 항목별로 쪼갠다. 센서, 통신, 연산, 구동, ZOH 다. ZOH 가 $T_s/2$ 를 차지한다는 걸 잊지 않는다.
3. 각 구간의 최악값을 구한다. 평균으로 계산하면 반드시 나중에 물린다.
4. 통신 방식을 고른다. 예산 안에 들어오는 것 중 가장 단순한 것으로 한다.
5. 측정한다. 계산은 틀린다. GPIO 토글과 오실로스코프, 또는 타임스탬프 히스토그램을 쓴다.
6. 런타임에 계속 감시한다. 주기 초과 카운터, [08편](/posts/08-basics-flow-control/)의 갱신 카운터, 워치독이다.

5번을 건너뛰는 게 가장 흔한 실수다. 데이터시트의 최대 1 Mbps 와 실제 시스템의 최악 지연은 다른 이야기다. 두 GPIO 를 토글해서 오실로스코프로 재는 30분이 며칠의 디버깅을 아낀다.

## 정리

- 제어가 통신에 요구하는 건 처리량이 아니라 지연의 상한과 일정함이다.
- 시간 지연은 크기는 그대로 두고 위상만 $\omega\tau$ 만큼 깎는다. $\omega_c\tau \lesssim 0.3$ rad 이 실용 기준이다.
- 통신 선택이 제어 대역폭의 상한을 정한다. 대역폭 200 rad/s 면 총 지연 예산이 1.5 ms 다.
- ZOH 가 $T_s/2$ 를 차지한다. 예산에서 가장 큰 항목인 경우가 많다.
- 지터는 지연보다 나쁘다. 일정한 지연은 보상할 수 있지만 지터는 할 수 없다.
- 지터 5% 는 속도 추정 오차 5% 가 되고 D 항이나 ESO 를 통해 진동과 소음으로 나온다.
- 실시간 사양은 평균이 아니라 최악으로 쓴다. 히스토그램의 꼬리가 시스템을 결정한다.
- 지터의 주범은 OS 스케줄링, 재전송, USB latency timer(기본 16 ms), 동적 메모리와 락이다.
- 결정성 확보는 우선순위(CAN)보다 폴링, 폴링보다 스케줄(EtherCAT), 그보다 스케줄과 공통 시각(DC) 순으로 강해진다.
- DC 가 주는 건 제때 도착을 넘어 동시에 반영이다. 다관절 동기의 근거다.
- 계산하고 반드시 측정하고 런타임에 감시한다.
