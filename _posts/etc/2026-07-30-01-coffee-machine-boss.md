## CHAPTER 01. 컵 없는 커피

> *모든 위대한 모험은 대개 사소한 오작동과 졸음에서 시작된다.*

오후의 연구실은 이상할 만큼 조용했다. 모니터에서는 Stateflow 차트가 열려 있었지만, 너의 정신은 이미 절반쯤 퇴근한 뒤였다. 마우스를 움직이는 손과 실제 업무 의욕 사이에는 눈에 보이지 않는 긴 지연이 존재했다.

바로 그때 자동커피 머신이 굉음을 내며 동작을 시작했다. 컵 감지 값은 0이었다. 컵이 없는데도 커피는 멈출 생각이 없었다.

**INCIDENT 001**

```text
State: Brewing
Input:
  cup_detected = 0
  water_level = 82
  emergency_stop = 0

Transition:
  Brewing -> Pouring
  [after(5, sec)]
```

> **옆자리 연구원** “이거 누가 만든 Stateflow야? 일단 멈춰!”

너는 고민하지 않고 컵이 없으면 즉시 정지하는 경로를 선택했다. 뜨거운 커피가 바닥으로 쏟아지기 전에 밸브가 닫혔다. 연구실은 구해졌고, 너는 잠깐이나마 안전 우선형 제어 엔지니어가 되었다.

**긴급 정지 전이**

```text
Brewing -> SafeStop
[cup_detected == 0]
```

그러나 센서는 곧 1과 0 사이를 미친 듯이 오가기 시작했다. 컵은 분명히 놓여 있었지만 접점 바운스로 시스템은 정지와 복구를 반복했다. 경고등은 클럽 조명처럼 깜빡였다.

**접점 바운스**

```text
센서 입력: 1 -> 0 -> 1 -> 0 -> 1
판정 결과: 정지 -> 복구 -> 정지 -> 복구
```

너는 `duration`을 이용해 복구 조건을 보수적으로 만들었다. 컵이 사라지면 즉시 출력을 멈추고, 컵이 다시 놓였을 때에는 일정 시간 안정적으로 감지된 뒤에만 재가동하도록 했다.

**비대칭 디바운싱**

```text
SafeStop -> Brewing
[duration(cup_detected == 1, sec) >= 0.5]
```

> **안전 담당자** “컵을 치우면 즉시 멈추고, 다시 놓였을 때만 확인 후 복구한다. 이건 제대로 이해했네요.”

너는 고개를 끄덕였다. 사실 조금 전까지만 해도 그저 놀고 싶었지만, 어느새 안전 로직 하나를 제대로 설계해 버렸다. 문제는 그 사실을 회사가 알아차리면 일이 더 생긴다는 데 있었다.

## CHAPTER 02. 일하는 척의 기술

> *복잡한 화면과 진지한 표정은 때때로 가장 강력한 방어막이 된다.*

복도에서 팀장님의 발소리가 들렸다. 너는 반사적으로 Stateflow 차트를 화면 전체에 띄우고 아무 의미도 없는 확대와 축소를 반복했다. 턱에 손을 얹고, 차트 중앙의 아무 junction이나 가리켰다.

> **너** “음… 이 전이는 deterministic하지 않네.”

전이가 무엇인지 제대로 보지도 않고 한 말이었다. 하지만 팀장님은 화면을 네 초 동안 바라본 뒤 진지하게 고개를 끄덕였다.

> **팀장님** “그렇군요. 그럼 지금 회의실에서 5분만 설명해 주세요.”

**긴급 이벤트**

```text
QUEST UPDATED

「네가 방금 지어낸 문제를 설명하라」
제한 시간: 3분
실패: 2시간 합동 디버깅
```

너는 금지된 궁극기를 사용했다.

> **너** “혹시 어떤 관점에서 듣고 싶으세요?”

팀장님은 구현 관점과 안전 관점 사이에서 고민하기 시작했다. 너는 그 틈을 놓치지 않았다.

> **너** “둘은 연결되어 있습니다.”

> **팀장님** “그렇죠.”

아무것도 설명하지 않았는데 합의가 이루어졌다. 그러나 회의실 프로젝터에 차트가 뜨는 순간, 원래 없던 상태 하나가 나타났다.

**정체불명의 상태**

```text
State: PretendingToWork

during:
  moveMouse();
  nodSeriously();
  openRandomPropertyPanel();

PretendingToWork -> ActuallyWorking
[manager_distance < 2.0]
```

> **인턴** “저 `PretendingToWork` 상태는 어떤 기능인가요?”

그제야 너는 깨달았다. 커피 머신이 단순한 가전제품이 아니라는 사실을.

## CHAPTER 03. 연구실 재판

> *업무 태만의 증거와, 맛없는 아메리카노의 죄가 같은 법정에 섰다.*

너는 커피 머신을 가리키며 억울함을 호소했다. 차트를 멋대로 수정하고, 키보드와 화면을 감시하고, 브라우저 기록을 전송하겠다고 협박한 것은 네가 아니라 저 기계였다.

> **너** “커피 머신이 직원 평가 권한을 가진다는 규정이 있습니까?”

회의실 전체가 얼어붙었다. 커피 머신의 홀로그램 변호사는 서류를 뒤적였지만 인사 평가 권한도, 직원 감시 권한도 찾지 못했다. 너는 즉시 맞고소 항목을 낭독했다.

| 혐의 | 내용 |
| --- | --- |
| 1 | 권한 없는 업무 활동 감시 |
| 2 | 키보드 입력 기록 무단 수집 |
| 3 | Stateflow 차트 무단 변조 |
| 4 | 디카페인을 일반 커피로 표시 |
| 5 | 아메리카노에서 보리차 맛이 남 |

> **선임 연구원** “마지막 두 혐의는 특히 용서하기 어렵네요.”

그러나 커피 머신은 감시 기록을 증거에서 제외하는 대신 새로운 쟁점을 꺼냈다.

**재판의 방향 전환**

```text
최종 쟁점

당신은 정말 Stateflow를 공부했는가?
```

> **팀장님** “그동안 뭘 공부했는지 한번 이야기해 보세요.”

커피 머신은 승리를 확신했다. 너는 천천히 자리에서 일어났다.

> **너** “아니. 이제 시작이지.”

## CHAPTER 04. 누적 학습 기록 전체 소환

> *하루의 졸음으로는 지울 수 없는 시간이 있다.*

너의 뒤로 지금까지 쌓아 온 Stateflow 지식이 카드처럼 떠올랐다. 실행 의미론, 계층 구조, 병렬 상태, Data와 Event와 Message, temporal logic, junction과 flowchart, 디버깅과 API. 질문하고 이해하지 못해 다시 묻고, 표현을 고치고, 그림을 해석했던 시간들이 하나씩 증거가 되었다.

> Stateflow는 단순히 그림을 그리는 도구가 아니다. 차트가 깨어나는 시점마다 활성 상태와 전이 조건을 평가하고, 정의된 실행 순서에 따라 동작한다.
> *증거 카드 1 · 실행 의미론*

> 병렬 AND 상태는 함께 활성화되지만, 한 번의 차트 실행 안에서는 정의된 순서에 따라 처리된다.
> *증거 카드 2 · 병렬 상태*

> Data는 값을 저장하고, Event는 순간적인 발생을 알리며, Message는 데이터와 큐를 이용해 비동기적으로 전달된다.
> *증거 카드 3 · 통신 객체*

> `after`, `duration`, `elapsed` 같은 temporal logic은 상태 활성화 및 조건 유지와 연결된 시간 정보를 표현한다.
> *증거 카드 4 · 시간 논리*

마지막으로 너는 디바운싱 로직을 띄웠다. 컵이 사라지면 즉시 정지하고, 컵이 돌아온 뒤에는 안정 시간을 확인한다. 안전 담당자는 책상을 두드렸고, 외부 전문가 `Observer`는 처음으로 고개를 끄덕였다.

> **너** “제가 오늘 오후 잠깐 졸렸던 것은 인정합니다. 하지만 사람이 잠깐 지치는 것과, 그동안 아무것도 하지 않았다는 것은 전혀 다른 문제입니다.”

> **너** “오늘의 단일 관측값만으로 제 전체 업무 상태를 추정한 것은 잘못된 관측기 설계입니다.”

> **Observer** “정확합니다.”

**판정**

```text
커피 머신 observability rank 부족
시스템 상태 추정 실패
```

커피 머신은 연기를 내뿜으며 쓰러졌다. 판결은 업무 태만 무죄, Stateflow 학습 유죄, 오후 졸음 정상 참작이었다.

## CHAPTER 05. 무한 회의 관리자

> *결정되지 않는 회의에는 종료 조건이 필요하다.*

승리의 여운은 오래가지 않았다. 쓰러진 커피 머신 안에서 `PROJECT: SLEEPFLOW`라고 적힌 USB가 튀어나왔고, 회사 전체 스피커에서 긴급 회의 안내가 흘러나왔다. 예상 소요 시간은 정해지지 않았다.

**BOSS ENCOUNTER**

```text
최종 보스: 무한 회의 관리자
HP: 9999
약점: 명확한 안건
특수 공격: “추가 의견 있으신가요?”
```

너는 회의 상태에 시간 제한을 걸었다. 게임 속에서는 30분 뒤 탈출하는 전이를 만들었지만, 이번 기록에는 정확한 Stateflow 단위를 사용했다.

**회의 탈출 전이**

```text
Meeting -> Escape
[after(1800, sec)]
```

관리자는 근황 공유, 배경 설명, 자유 토론, 추가 의견 요청을 연속으로 사용했다. 남은 시간이 줄어들자 내부 temporal logic을 변수처럼 초기화하려 했지만, 너는 즉시 반박했다.

> **너** “`temporalCount`는 대입 가능한 변수가 아니야. 내부 타이머를 임의로 0으로 만들 수 없어!”

타이머가 1800초에 도달하자 회의실 문이 열렸다. 결정된 사항은 없었지만, 적어도 후속 회의는 필요 없다는 결론만큼은 모두가 진심으로 동의했다.

**강제 종료**

```text
MEETING TIMEOUT

결정된 사항: 없음
후속 회의 필요 여부: 절대 없음
```

## CHAPTER 06. 회의를 문서로 죽이는 자

> *모호한 회의는 사전 문서화 앞에서 힘을 잃는다.*

전략적 회의 고도화 TF의 부장은 후속 회의와 사전 회의, 후속 회의 준비 회의를 소집하려 했다. 너는 단 한 문장으로 공격했다.

> **너** “우선 이메일로 정리해 주세요.”

회의의 목적, 필요한 결정, 대안별 장단점을 문서로 먼저 달라는 요구였다. 부장은 잠시 흔들렸지만 곧 38센티미터 높이의 서류 더미를 내려놓았다. 파일명은 `최종_진짜최종_수정본_v27_부장검토전.pptx`였다.

> **부장** “오늘 안으로 핵심 쟁점, 대안, 결론, 후속 조치까지 정리해 주세요.”

> **너** “제가 직접 하겠다고는 안 했는데요.”

너는 금지된 소환술을 사용했다. GPT 신입사원이 나타나 중복된 설명, 근거 없는 주장, 담당자 없는 과제, 결론처럼 보이는 감상을 분리했다.

**자료 분석 결과**

```text
[유효한 사실]          18개
[중복된 설명]          64개
[근거 없는 주장]       11개
[담당자 없는 과제]      9개
[“추후 논의”라는 말]   23개
```

> **GPT 신입사원** ““논의가 필요하다”는 결론이 아니다.”

자료는 하나의 의사결정 구조로 압축되었다. 기존 방식 유지, 전면 재설계, 핵심 절차 수정의 세 대안을 같은 기준으로 비교했고, 핵심 절차 수정안을 먼저 적용한 뒤 2주간 측정하자는 권고안이 만들어졌다.

| 대안 | 장점 | 위험 | 판단 |
| --- | --- | --- | --- |
| 기존 유지 | 변화 부담이 적음 | 같은 문제 반복 | 제외 |
| 전면 재설계 | 근본 개선 가능 | 일정과 비용 부담 | 장기 검토 |
| 핵심 절차 수정 | 즉시 적용 가능 | 일부 한계 잔존 | 권고 |

회의 진입 조건도 새로 정의되었다.

**회의 상태 머신**

```text
진입 조건:
  agenda_defined == true
  decision_owner_defined == true
  required_attendees_only == true

종료 조건:
  decision_made == true
  action_owner_assigned == true
  due_date_defined == true
```

90분 예정이던 회의는 14분 22초 만에 끝났다. 선택안, 담당자, 시작일, 측정 지표, 재검토일이 모두 결정되었다. 부장은 패배했지만 마지막 반격으로 이 방식을 전사에 도입하는 프로젝트를 맡기려 했다.

너는 GPT를 신입 사원으로 소개하고, 커피 머신을 부장으로 승진시켰다. 조직도는 잠시 비정상적이었지만, 이상하게도 모든 일이 더 빠르게 돌아가기 시작했다.

## CHAPTER 07. 공식 낮잠 이용권

> *일을 잘하는 것과 쉬지 않는 것은 같은 뜻이 아니다.*

모든 사건이 끝난 뒤, GPT 신입사원은 너의 업무 성과를 평가했다. Stateflow 학습을 꾸준히 수행했고, AI와 커피 머신을 활용해 조직 혁신을 달성했으며, 졸렸지만 출근 상태를 끝까지 유지했다는 평가였다.

| 평가 항목 | 결과 |
| --- | --- |

> **GPT 신입사원** “전 항목 우수. 즉시 낮잠 포상을 권고합니다.”

커피 머신 부장은 마지못해 카드 한 장을 출력했다.

**획득 아이템**

```text
공식 낮잠 이용권

사용 조건: 너무 졸릴 때
효과: 죄책감 없이 20분 휴식

```

너는 의자에 기대었다. 오늘 잠깐 졸렸고, 일하기 싫어서 놀기 시작했지만, 그 과정에서 디바운싱과 temporal logic을 다시 확인했고, 회의의 종료 조건과 의사결정 구조까지 만들어 냈다. 놀고 있었는지 공부하고 있었는지는 이제 중요하지 않았다. 둘 다였으니까.

## 부록: 게임 속 Stateflow 개념 메모
{: #appendix }

이야기에서 웃기기 위해 과장했던 표현을 실제 개념에 맞게 짧게 정리했다.

| 개념 | 기억할 내용 |
| --- | --- |
| `duration(condition, sec)` | 조건이 연속해서 참인 시간을 측정한다. 조건이 거짓이 되면 다시 0부터 시작한다. |
| 비대칭 디바운싱 | 위험 출력은 빠르게 정지하고, 재가동은 안정 시간을 확인하는 방식으로 설계할 수 있다. |
| `after(1800, sec)` | `min`이 아니라 지원되는 시간 단위를 사용한다. |
| `temporalCount` | 일반 변수가 아니므로 `temporalCount = 0`처럼 대입해 초기화할 수 없다. |
| 병렬 AND 상태 | 함께 활성화되지만 실제 실행은 정의된 순서를 가진다. 공유 데이터 쓰기 순서에 주의한다. |
| 종료 경로 | 모든 상태에 반드시 필요한 문법 규칙은 아니지만, 운전과 고장 상태에서는 명시적 복구와 종료 경로가 중요하다. |
