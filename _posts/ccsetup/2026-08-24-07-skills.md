명령과 Skill 은 둘 다 마크다운 파일이고 둘 다 `/이름` 으로 부를 수 있다. 그런데 쓰임이 다르다.

## 1. 문서가 말하는 정의

문서에 따르면 Skill 은 지식, 워크플로, 지시를 담은 마크다운 파일이다. `/deploy` 처럼 명령으로 부를 수도 있고, **관련이 있을 때 Claude 가 자동으로 불러올 수도 있다.**

이 두 번째가 명령과 갈리는 지점이다.

| | 슬래시 명령 | Skill |
| --- | --- | --- |
| 언제 도나 | 내가 부를 때 | 내가 부를 때 **또는 관련될 때** |
| 담는 것 | 절차 | 지식과 작업 방식 |
| 크기 | 한 회차 | 하나의 사고 방식 |

## 2. 언제 Skill 로 만드나

내 기준은 이렇게 정리됐다.

**"무엇을 할지" 가 아니라 "어떻게 생각할지" 일 때.**

절차는 명령이 맞다. 1번 하고 2번 하고 3번 한다. 반면 "이런 상황에서는 이렇게 접근한다" 는 절차가 아니라 태도다. 그건 Skill 쪽이다.

**여러 작업에 걸쳐 쓰일 때.**
명령 하나에만 필요한 것이면 그 명령 안에 쓰면 된다. 여러 명령이 같은 방식을 공유하면 Skill 로 뺀다.

## 3. 실제로 만든 것 하나

계획이나 결정을 **캐묻는** Skill 을 하나 붙였다. 목적이 하나다.

> 결정이 열려 있는 상태에서 곧장 답을 내지 않는다. 물어야 할 것을 먼저 세운다.

동작 방식이 이렇다.

1. 결정들을 트리로 본다. 어떤 결정이 다른 결정에 매달려 있는지
2. **지금 물을 수 있는 것**만 고른다. 앞 결정이 안 정해져서 지금 물으면 답을 못 하는 것은 다음 라운드로 미룬다
3. 그것들을 한 라운드에 묶어 번호를 매겨 묻는다. **질문마다 권장답을 붙인다**
4. 답을 받으면 트리가 바뀐다. 다시 계산해서 다음 라운드를 묻는다
5. 물을 것이 없어지면 끝난다

3번의 "권장답을 붙인다" 가 실제로 큰 차이를 만들었다. 질문만 스무 개 던지면 대답하기가 일이 된다. 권장답이 붙어 있으면 대부분은 "그걸로" 하고 넘어가고, 다른 것만 고른다.

## 4. 왜 이게 명령이 아니라 Skill 인가

이 절차 자체는 명령으로도 만들 수 있다. Skill 로 둔 이유가 둘이다.

**여러 작업 앞에 붙는다.** 설계를 시작할 때, 방향을 정할 때, 방안을 고를 때. 매번 다른 작업이지만 앞에 붙는 것은 같다.

**자동으로 걸릴 수 있다.** 대화에 "어떻게 할까", "어느 방안이", "정해야" 같은 말이 나오면 Claude 가 이걸 꺼낼 수 있다. 내가 매번 부를 필요가 없다.

## 5. 🔴 아무 데나 붙이면 안 된다

이걸 만들고 나서 모든 작업 앞에 붙이려다 멈췄다.

**이미 절차가 완성된 작업에는 안 붙인다.** 절차가 확립된 일에 캐묻기를 얹으면 진행표가 둘이 된다. 둘이 되면 둘 다 못 믿는다.

기준을 이렇게 갈랐다.

| 작업 | Skill 을 앞에 붙이나 |
| --- | --- |
| 설계 결정이 열려 있다 | ✅ 붙인다 |
| 방향을 정해야 한다 | ✅ 붙인다 |
| 절차가 이미 굳었다 | 🔴 **안 붙인다** |
| 검사나 집계처럼 답이 정해진 일 | 🔴 안 붙인다 |

## 6. 그리고 캐묻기만 하고 끝내지 않는다

Skill 은 "무엇을 할지" 를 정해준다. "어떻게 돌릴지" 는 정해주지 않는다.

그래서 캐묻기가 끝나면 실행 쪽으로 넘어가야 한다. 그 경계를 안 두면 질문만 잔뜩 하고 아무것도 안 한 회차가 된다. 실제로 그럴 뻔했다.

## 7. 남의 Skill 을 통째로 받지 않는 이유

Skill 은 묶음으로 배포되기도 한다. 편하지만 두 가지를 확인하고 받는 편이 낫다.

**설명이 매 세션 상주한다.** Skill 이 자동으로 걸리려면 언제 걸릴지가 항상 보여야 한다. 개수가 늘면 그만큼 자리를 차지한다.

**전제가 다를 수 있다.** 특정 도구나 작업 흐름을 전제한 Skill 은 그 전제가 없는 환경에서 엉뚱하게 발동한다.
