## 1. 프레임 설정이 통신을 아예 막는 이유

[01편](/posts/01-uart-async-meaning/)에서 봤듯 프레임은 시작과 데이터와 패리티와 정지로 이뤄진다. 8N1(10비트)로 보내는데 8E1(11비트)로 받으면 이렇게 된다. 수신기는 송신자의 정지 비트인 HIGH 를 패리티로 읽고, 다음 바이트의 시작 비트를 정지 비트 자리에서 본다. LOW 를 정지 비트로 읽으니 Framing Error 다.

값이 조금 이상한 게 아니라 아예 안 된다. 그래서 진단이 오히려 쉽다. Framing Error 가 계속 뜨면 보율 아니면 프레임 설정이다.

## 2. 각 구간의 세부

### 시작 비트는 1개 고정이고 협상 불가다

항상 1비트이고 항상 LOW 다. 이건 바꿀 수 없다. [02편](/posts/02-uart-baud-error-budget/)에서 봤듯 동기의 기준점이기 때문이다.

### 데이터 비트는 5~9비트다

| 비트 수 | 쓰임 |
| --- | --- |
| 5 | 보도(Baudot) 텔레타이프. 역사 유물이다 |
| 6 | 거의 쓰지 않는다 |
| 7 | ASCII 라면 충분하다. 옛 터미널과 Modbus ASCII |
| 8 | 기본이다. 바이너리 데이터를 다룬다 |
| 9 | 특수하다. 아래에서 다룬다 |

MCU 데이터시트에서 9비트 모드가 헷갈리는 부분이다.

| 상황 | 실제 의미 |
| --- | --- |
| 워드 길이 9 에 패리티 사용 | 데이터 8비트에 패리티 1비트로 총 9비트다. 곧 `8E1` 이나 `8O1` 설정이 하드웨어에서는 9비트 워드다 |
| 워드 길이 9 에 패리티 없음 | 진짜 9비트 데이터다. 멀티드롭 주소 지정에 쓴다 |

진짜 9비트 데이터의 용도는 멀티드롭 주소 지정 모드다. 9번째 비트를 이 바이트가 주소인지(1) 데이터인지(0) 표시하는 데 쓴다. 슬레이브는 주소 바이트만 인터럽트로 받고 자기 주소가 아니면 뒤따르는 데이터 바이트들을 하드웨어가 무시한다. mute 모드라고 부른다.

효과는 자기 것이 아닌 트래픽에 CPU 를 쓰지 않는다는 것이다. RS-485 멀티드롭에서 노드가 많을 때 의미가 크다. 다만 상대도 지원해야 하고 Modbus 는 이 방식을 쓰지 않는다. 주소를 일반 데이터 바이트로 보낸다.

### 패리티는 다섯 가지다

| 설정 | 규칙 |
| --- | --- |
| N (None) | 패리티 비트가 없다 |
| E (Even) | 데이터와 패리티의 1 개수가 짝수가 되게 한다 |
| O (Odd) | 홀수가 되게 한다 |
| M (Mark) | 항상 1 이다. 검사가 아니라 9비트 모드 흉내다 |
| S (Space) | 항상 0 이다. 마찬가지다 |

데이터 `0x41` 은 `01000001` 이라 1의 개수가 2개로 짝수다. Even 이면 패리티가 0 이고 Odd 면 1 이다. 데이터 `0x43` 은 `01000011` 이라 1의 개수가 3개로 홀수다. Even 이면 패리티가 1 이고 Odd 면 0 이다.

[기초 07편](/posts/07-basics-error-detection/)에서 봤듯 패리티는 홀수 개 오류만 잡는다. 2비트가 뒤집히면 그냥 통과한다. 그리고 어차피 상위 계층인 Modbus 에서 CRC 를 하니 중복이다.

그런데 진단 가치는 있다. Parity Error 카운터가 늘고 있다는 건 물리계층이 나빠지고 있다는 뜻이다. CRC 는 프레임 단위로 깨졌다만 알려주지만 패리티는 바이트 단위로 알려준다. 어느 바이트에서 자주 깨지는지, 특정 비트 패턴에서 깨지는지 같은 세밀한 정보가 나온다.

그래서 8E1 을 쓰되 패리티 에러를 카운터로만 쓰고 프레임 판정은 CRC 에 맡기는 조합이 실무에서 합리적이다. Modbus RTU 기본값이 8E1 인 것도 이 맥락이다.

### 정지 비트

02편에서 본 대로 수신 오차 예산 관점에서는 1개가 유리하다. 2개를 쓰는 이유는 다른 데 있다.

| 정지 비트 | 왜 |
| --- | --- |
| 1 | 기본이다. 오버헤드가 최소다 |
| 1.5 | 5비트 데이터 모드와 짝이다. 거의 쓰지 않는다 |
| 2 | 수신 소프트웨어에 처리 시간을 준다. 오래된 장비 호환이나 광절연 트랜시버의 느린 전이를 흡수하는 데도 쓴다 |

## 3. 오버헤드 계산

| 설정 | 총 비트 | 데이터 비트 | 효율 | 115200 에서 바이트당 |
| --- | --- | --- | --- | --- |
| 8N1 | 10 | 8 | 80% | 86.8 µs |
| 8N2 | 11 | 8 | 73% | 95.5 µs |
| 8E1 | 11 | 8 | 73% | 95.5 µs |
| 8E2 | 12 | 8 | 67% | 104.2 µs |
| 7E1 | 10 | 7 | 70% | 86.8 µs |
| 9N1 (진짜 9비트) | 11 | 9 | 82% | 95.5 µs |

8N1 에서 8E1 로 바꾸면 처리량이 10% 준다. 115200 에서 11520 이 10473 바이트/초가 된다. Modbus 트랜잭션 시간 계산에 영향을 준다.

## 4. 프레임 설정 불일치 진단표

| 송신 | 수신 | 증상 |
| --- | --- | --- |
| 8N1 | 8N1 | 정상이다 |
| 8N1 | 8E1 | Framing Error 가 지속된다. 정지 비트를 패리티로 읽는다 |
| 8E1 | 8N1 | 패리티 비트를 정지 비트로 읽는다. 패리티가 1일 때만 우연히 통과하고 0이면 Framing Error 라 간헐적으로 실패한다 |
| 8E1 | 8O1 | 패리티가 우연히 맞는 경우를 빼고 거의 모든 바이트에서 Parity Error 가 난다 |
| 8N1 | 7N1 | MSB 가 잘리고 프레임이 밀린다 |
| 8N2 | 8N1 | 대개 동작한다. 여분의 정지 비트는 idle 로 보인다 |
| 8N1 | 8N2 | 두 번째 정지 비트 자리에서 다음 시작 비트를 만난다 |

세 번째 줄인 8E1 송신에 8N1 수신이 가장 악질이다. 데이터에 따라 되기도 하고 안 되기도 한다. 가끔 통신이 안 된다는 증상의 원인 중 하나다.

그래서 진단 순서는 보율 실측, 양쪽 문서에서 프레임 설정 확인, 배선, 물리계층 순이다.

## 5. 설정을 타입으로 표현하기

문자열 `"8N1"` 을 파싱하거나 매직 넘버를 쓰면 실수가 난다. 타입으로 만들면 컴파일러가 막아준다.

```cpp
// comm_serial/frame_format.hpp
#pragma once
#include <cstdint>

enum class Parity   : std::uint8_t { None, Even, Odd, Mark, Space };
enum class StopBits : std::uint8_t { One, OneAndHalf, Two };

struct FrameFormat {
    std::uint8_t data_bits{8};
    Parity       parity{Parity::None};
    StopBits     stop{StopBits::One};

    // 프레임 전체 비트 수. 처리량과 타임아웃 계산의 기초다
    constexpr double total_bits() const {
        double n = 1.0 + data_bits;                        // 시작과 데이터
        if (parity != Parity::None) n += 1.0;
        n += (stop == StopBits::One) ? 1.0
           : (stop == StopBits::OneAndHalf) ? 1.5 : 2.0;
        return n;
    }
    constexpr double byte_time_us(std::uint32_t baud) const {
        return total_bits() * 1e6 / baud;
    }
};

// Modbus RTU 규격 기본값인 8E1
inline constexpr FrameFormat kModbusRtuDefault{8, Parity::Even, StopBits::One};
static_assert(kModbusRtuDefault.total_bits() == 11.0);
static_assert(kModbusRtuDefault.byte_time_us(9600) > 1145.0 &&
              kModbusRtuDefault.byte_time_us(9600) < 1147.0);   // 약 1145.8 µs
```

`total_bits()` 가 나중에 여러 곳에서 쓰인다. Modbus 침묵 시간, 트랜잭션 타임아웃, 버스 점유 시간 계산이다. 한 군데서 계산하고 재사용하면 설정을 바꿨을 때 전부 따라온다.

## 6. 실무 권장 조합

| 상황 | 권장 | 이유 |
| --- | --- | --- |
| 일반 디버그 콘솔 | 8N1 | 표준이고 효율이 최대다 |
| Modbus RTU | 8E1 | 규격 기본값이다. 상대 장비가 대개 이걸 기대한다 |
| Modbus RTU 인데 상대가 8N1 만 지원 | 8N2 | 규격이 인정하는 대안이다. 패리티를 안 쓰면 정지 비트를 2개로 해서 프레임 길이 11비트를 유지한다 |
| 노이즈가 심한 환경 | 8E1 에 CRC | 패리티는 진단용이고 판정은 CRC 가 한다 |
| 최대 처리량이 필요할 때 | 8N1 | |

패리티를 안 쓰면 정지 비트 2개라는 것은 Modbus 규격이 명시한 규칙이다. 문자 프레임을 항상 11비트로 유지하려는 것이고 침묵 시간 계산이 그 전제 위에 서 있다.

## 정리

- 프레임 설정이 안 맞으면 값이 이상한 게 아니라 아예 안 되므로 진단은 오히려 쉽다.
- 시작 비트는 1개 LOW 고정이다. 동기 기준점이라 협상이 불가능하다.
- 9비트 모드는 두 얼굴이다. 8비트에 패리티이거나 진짜 9비트(멀티드롭 주소 지정)다.
- 진짜 9비트 모드의 가치는 슬레이브가 자기 것이 아닌 트래픽에 CPU 를 쓰지 않는다는 것이다.
- 패리티는 홀수 개 오류만 잡아 판정용으로는 약하지만 바이트 단위 진단 신호로는 유용하다.
- 정지 비트 2개는 수신 오차 예산에는 불리하고 처리 시간과 호환성에는 유리하다.
- 오버헤드는 8N1 이 80%, 8E1 이 73% 다. 처리량이 10% 준다.
- 가장 악질 불일치는 8E1 송신에 8N1 수신이다. 데이터에 따라 되다 안 되다 한다.
- 프레임 설정을 타입으로 만들고 `total_bits()` 를 한 군데서 계산해 재사용한다.
- Modbus 규칙은 패리티를 안 쓰면 정지 비트 2개다. 프레임을 11비트로 유지한다.
