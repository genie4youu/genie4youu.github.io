같은 지시를 세 번째 반복해서 쓰고 있다면 그건 프롬프트 문제가 아니다.

## 1. 세 가지가 반복된다

도구를 쓰다 보면 같은 불편이 돌아온다.

**잊는다.** 세션마다 "이건 이렇게 해줘" 를 다시 쓴다. 대화가 길어지면 앞에 쓴 것도 흐려진다.

**틀린다.** 지켜야 할 규칙이 열 개면 아홉 개는 지키고 하나를 놓친다. 어느 하나를 놓쳤는지는 결과를 봐야 안다.

**재현이 안 된다.** 같은 일을 두 번 시키면 두 번 다르게 한다. 잘 됐을 때 왜 잘 됐는지 모르고, 안 됐을 때 어디가 달랐는지 모른다.

## 2. 프롬프트를 더 잘 쓰면 되지 않나

어느 정도까지는 된다. 그런데 셋 다 **양이 늘면 나빠지는 성질**을 갖는다.

| | 프롬프트로 풀 때 | 한계 |
| --- | --- | --- |
| 잊는다 | 매번 붙여 넣는다 | 붙여 넣는 것을 잊는다 |
| 틀린다 | 규칙을 더 세게 쓴다 | 규칙이 길어질수록 뒤쪽이 묻힌다 |
| 재현이 안 된다 | 순서를 자세히 적는다 | 자세히 적어도 지킬지는 그때그때다 |

공통점이 있다. **전부 모델의 판단에 기대고 있다.** 판단은 확률적이라 대부분 맞고 가끔 틀린다. 가끔이 문제가 되는 일에서는 이 구조로 못 간다.

## 3. 층을 하나 만든다

해법은 프롬프트를 잘 쓰는 것이 아니라 **프롬프트 바깥에 층을 만드는 것**이다.

공식 문서는 그 층을 몇 갈래로 나눠 제공한다.

| 갈래 | 무엇을 고정하나 |
| --- | --- |
| **슬래시 명령** | 절차. 같은 순서로 도는 것 |
| **서브에이전트** | 역할과 권한. 누가 무엇을 할 수 있는지 |
| **Skill** | 지식과 작업 방식. 언제 꺼낼지를 포함해 |
| **Hook** | 강제. 모델 판단을 안 거치고 도는 것 |
| **MCP** | 도구. 바깥 시스템에 붙는 통로 |

다섯이 서로 다른 것을 고정한다. 그래서 **무엇이 반복되는가**에 따라 고를 갈래가 달라진다.

## 4. 어느 갈래를 고를 것인가

이 연재의 실질적인 질문이 이것이다. 미리 답을 요약하면 이렇게 갈린다.

```
같은 순서를 반복한다        → 슬래시 명령
같은 역할을 반복한다        → 서브에이전트
같은 판단 기준을 반복한다   → Skill
반드시 지켜져야 한다        → Hook
바깥 시스템을 봐야 한다     → MCP
```

마지막에서 두 번째가 이 목록에서 성격이 다르다. 앞의 셋은 **모델이 잘 하도록 돕는 것**이고, Hook 은 **모델이 안 해도 되게 만드는 것**이다. 06편에서 따로 다룬다.

## 5. 만들기 전에 물어볼 것

층을 만드는 데도 비용이 든다. 파일이 늘고, 그 파일을 유지해야 하고, 잘못 만들면 방해가 된다.

만들기 전에 두 가지를 확인하는 편이 낫다.

**정말 반복되는가.** 두 번 한 일은 아직 반복이 아니다. 세 번째에 만들어도 늦지 않다.

**절차가 굳었는가.** 아직 방법을 찾는 중이면 고정하면 안 된다. 잘못된 절차가 굳으면 바꾸기가 더 어렵다.
