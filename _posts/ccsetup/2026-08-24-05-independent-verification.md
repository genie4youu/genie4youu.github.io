세팅을 하다 만난 문제 중 가장 오래 붙잡은 것이 이거였다.

## 1. 출력이 같다

작업을 끝내고 "확인해 줘" 라고 하면 확인해 준다. 그리고 대개 이렇게 답한다.

```
검사 결과 문제 없습니다. 실패 0건입니다.
```

이 문장은 두 가지 상황에서 똑같이 나온다.

- 실제로 전부 검사했고 문제가 없었다
- **검사 대상이 0건이었다**

둘째 경우가 무서운 이유는 이게 실패처럼 안 보이기 때문이다. 스크립트가 조용히 빈 목록을 돌면 루프가 안 돌고 끝나고, 출력은 성공과 구분되지 않는다.

## 2. 두 가지 장치

이 문제에 두 가지를 걸었다.

**첫째, 모집단 크기를 함께 요구한다.**

검증자의 반환 형식에 "무엇을 몇 개 대상으로 검사했는가" 를 필수 항목으로 넣는다. 0건을 보고하려면 몇 개 중 0건인지 밝혀야 한다.

```
❌ 문제 없음
✅ 대상 47개 검사, 문제 0건. 방법: 파일명 목록과 목차 링크 대조
```

이것만으로 앞의 두 상황이 갈린다.

**둘째, 검증자를 다른 컨텍스트에 둔다.**

같은 대화 안에서 자기 결과를 보면 통과시킨다. 03편의 격리 성질이 여기서 도구가 된다. 검증자를 서브에이전트로 두면 **만든 쪽의 판단을 안 갖고** 시작한다.

## 3. 무엇을 안 주는가

여기가 실제로 자주 무너지는 자리다. 검증자에게 주면 안 되는 것 셋.

🔴 **만든 쪽의 보고.** "이 에이전트가 이렇게 판단했는데 맞는지 봐 달라" 라고 하면 그 판단이 앵커가 된다. 대상만 준다. 파일 경로와 판정 기준, 그게 전부다.

🔴 **통과가 목표라는 신호.** "마지막 확인입니다", "곧 발행합니다" 가 붙으면 통과 쪽으로 기운다.

🔴 **쓰기 도구.** 04편의 이야기다. 고칠 수 있으면 지적하는 대신 고친다.

## 4. 검증자에게 적어둘 것

정의 파일에 원칙을 몇 줄 박아두면 매번 안 써도 된다. 내가 넣은 것들.

| 원칙 | 왜 |
| --- | --- |
| 앞선 작업의 완료 보고를 근거로 삼지 않는다 | 위 3번 |
| "0건" 과 "전부 통과" 를 최우선으로 의심한다 | 위 1번 |
| 합계가 맞는 것은 검증이 아니다. 총계와 분해를 각각 대조한다 | 총계만 맞고 내역이 틀린 경우가 실제로 있다 |
| "전부", "유일", "없다" 는 전수 확인 후에만 쓴다 | 표본으로 단정어를 쓰면 그 뒤가 다 무너진다 |
| 수정하지 않는다. 목록만 낸다 | 위 3번 |

마지막 두 줄이 특히 값을 했다. **단정어를 제한하는 것**이 생각보다 크게 작동한다.

## 5. 관점 대역이라는 변형

검증자와 성격이 다른 것을 하나 더 만들었다. **처음 보는 사람으로 읽는** 에이전트다.

판정 기준이 하나다.

> **"내가 아는가" 가 아니라 "이 문서가 설명했는가" 로만 본다.**

아는 것으로 빈칸을 메우면 무용지물이 된다. 그래서 읽는 방법도 정해둔다. 순서대로 한 번만 읽고 되돌아가지 않는다. 되돌아가야 이해되면 그것이 곧 결함이다.

이 에이전트를 붙이고 나서 알게 된 것이 있다. **내가 쓴 글이 틀린 게 아니라 앞 문서를 전제하고 있었다.** 사실 관계는 맞는데 읽는 사람이 못 따라오는 상태였고, 그건 사실 검증으로는 안 잡힌다.

## 6. 비용과 기준

검증자를 붙이면 그만큼 더 돈다. 항상 붙일 필요는 없다.

| 붙인다 | 안 붙인다 |
| --- | --- |
| 결과가 되돌리기 어렵다 (발행, 배포, 삭제) | 되돌리기 쉽다 |
| 사람이 그 결과를 근거로 판단한다 | 중간 산출물이다 |
| 그럴듯한데 확인이 어렵다 | 바로 확인된다 |

첫 줄이 실제 기준이다. **되돌릴 수 있으면 안 붙여도 된다.**
