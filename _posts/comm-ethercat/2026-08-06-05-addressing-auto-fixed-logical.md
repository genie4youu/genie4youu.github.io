## 1. 문제, 슬레이브에 주소가 없다

[이더넷 01편](/posts/01-ethernet-frame-mac/)에서 봤듯 EtherCAT 슬레이브에는 MAC 주소도 IP 주소도 없다. 공장에서 나올 때 아무 식별자가 없다. 그런데 마스터는 "3번째 슬레이브의 레지스터 0x0130을 읽어라" 같은 일을 해야 한다.

EtherCAT는 이 문제를 네 가지 주소 방식으로 푼다. 각각 쓰이는 시점이 다르고 부팅 절차가 그 순서를 따라간다.

| 방식 | 명령 | 언제 쓰나 |
| --- | --- | --- |
| 자동 증가 | `APRD` `APWR` `APRW` | 부팅 초기, 주소가 아직 없을 때 |
| 설정 주소 | `FPRD` `FPWR` `FPRW` | 주소를 배정한 뒤, 특정 슬레이브 지목 |
| 브로드캐스트 | `BRD` `BWR` `BRW` | 전체에게 한 번에 |
| 논리 주소 | `LRD` `LWR` `LRW` | 운전 중 프로세스 데이터 |

## 2. 자동 증가 주소, 위치로 지목한다

주소가 없어도 "몇 번째" 로 지목하는 방법이다. Datagram의 주소 필드 앞 16비트를 위치 카운터로 쓰고, 슬레이브를 지날 때마다 +1 된다.

마스터가 위치 0으로 보내면 슬레이브 1이 "위치가 0이니 내 것" 이라 판단하고 처리한 뒤 WKC를 올리고 위치를 1로 만들어 내보낸다. 슬레이브 2는 위치가 1이니 자기 것이 아니고 +1만 해서 통과시킨다.

"위치 값이 0인 슬레이브가 처리한다" 는 규칙 하나로 N번째를 지목한다. 각 슬레이브는 자기가 몇 번째인지 몰라도 되고 카운터만 올리면 된다.

실제 구현에서는 음수(2의 보수)로 시작한다. 3번째를 지목하려면 `-2`(=0xFFFE)로 보내서 슬레이브 3에서 0이 되게 한다. SOEM의 `ec_APRD(ADP, ADO, ...)` 에서 ADP가 그 값이다.

### 이걸로 하는 일, 부팅 시 스캔

1. `BRD` 로 슬레이브 개수를 센다. WKC가 곧 개수다
2. 각 위치에 `APRD` 를 보내 정보를 읽는다. Vendor ID, Product Code, 지원 기능(DC, FMMU 개수, SM 개수)
3. `APWR` 로 각 슬레이브에 설정 주소를 써 넣는다 (레지스터 0x0010 = Configured Station Address)
4. 이제부터는 `FPRD` 와 `FPWR` 로 직접 지목할 수 있다

3번이 전환점이다. 이후로는 위치가 아니라 배정한 주소로 지목하고, 그러면 슬레이브 순서에 의존하지 않는 코드를 쓸 수 있다.

다만 배선 순서를 바꾸면 위치가 바뀌므로 주소 배정도 바뀐다. "슬레이브 3번" 은 논리적 이름이 아니라 물리적 순서다. 01편에서 말한 "토폴로지 자유도를 포기했다" 의 구체적 모습이다.

## 3. 설정 주소

마스터가 배정한 16비트 주소로 직접 지목한다. `FPRD(주소=1001, 오프셋=0x0130, 길이=2)` 를 보내면 각 슬레이브가 자기 station address가 1001인지 확인하고 맞는 슬레이브만 처리한다.

| 쓰는 곳 | |
| --- | --- |
| 특정 슬레이브의 레지스터 읽기와 쓰기 | ESM 상태 확인과 변경 (08편) |
| 메일박스 통신 | SDO 등 (11편) |
| SM과 FMMU 설정 | 06·07편 |
| 진단 | 포트별 CRC 카운터 읽기 (16편) |

관례상 주소를 1001, 1002 순으로 배정하는 경우가 많다. SOEM도 그렇게 한다. 0을 피하는 건 "주소 미설정" 과 구분하기 위해서다.

## 4. 브로드캐스트

모든 슬레이브가 처리한다. WKC가 슬레이브 개수만큼 올라간다.

### BRD의 특별한 성질, 논리 OR

여러 슬레이브가 같은 자리를 읽으면 읽은 값들이 논리 OR로 합쳐진다. 각 슬레이브가 자기 값을 프레임의 값과 OR 해서 덮어쓰기 때문이다.

이게 진단에 유용하다.

| 활용 | 방법 |
| --- | --- |
| 슬레이브 개수 세기 | `BRD` 를 아무 레지스터에. WKC가 곧 개수 |
| 전부 OP 상태인가 확인 | AL Status를 BRD. 하나라도 다르면 OR 결과가 달라진다 |
| 오류 비트 확인 | 오류 플래그를 BRD. 하나라도 서 있으면 1 |

"모두가 같은 상태인가" 를 프레임 하나로 확인할 수 있다. 슬레이브가 100개여도 Datagram 하나면 된다. SOEM의 `ec_statecheck(0, EC_STATE_OPERATIONAL, timeout)` 이 슬레이브 0(전체)에 대해 이 방식을 쓴다.

`BWR` 은 설정에 쓴다. 부팅 시 전체를 INIT 상태로 리셋하거나 전체 FMMU를 초기화하는 식이다.

## 5. 논리 주소, 제어 루프의 주력

### 문제

프로세스 데이터를 설정 주소로 주고받으면 슬레이브마다 Datagram이 하나씩 필요하다. 6축이면 6개이고 오버헤드가 12 × 6 = 72바이트다. 그리고 슬레이브마다 물리 메모리 배치가 달라서 마스터가 그걸 다 알아야 한다.

### 해법, 4 GB 논리 주소 공간

마스터가 하나의 큰 가상 주소 공간(32비트 = 4 GB)을 만들고 각 슬레이브의 데이터가 그 공간의 어느 자리인지 배정한다. 축1 입력, 축1 출력, 축2 입력, 축2 출력 순으로 이어 붙인 하나의 이미지가 만들어지고 `LRW` 하나로 그 전체를 읽고 쓴다.

각 슬레이브는 자기 담당 구간만 처리한다. "논리 주소 0x0010부터 0x0017은 내 물리 메모리 0x1200이다" 를 아는 장치가 FMMU다.

### 얼마나 절약되나

6축, 축당 입력 8과 출력 8 바이트 기준이다.

| 방식 | Datagram 수 | 오버헤드 | 데이터 | 총 프레임 |
| --- | --- | --- | --- | --- |
| FPRW (슬레이브별) | 6 | 72 B | 96 B | 208 B |
| LRW (하나로) | 1 | 12 B | 96 B | 148 B |

29% 절약이고 슬레이브가 늘수록 격차가 커진다. 30개면 FPRW는 오버헤드만 360바이트인데 LRW는 12바이트다.

그리고 마스터 코드가 훨씬 단순해진다. 슬레이브마다 다른 물리 주소를 관리할 필요 없이 연속된 메모리 하나(IOmap)만 다루면 된다.

### 마스터에서 보이는 모습

```cpp
// SOEM 에서 IOmap 은 그냥 바이트 배열이다
static std::array<std::uint8_t, 4096> io_map;

ec_config_map(io_map.data());   // 이 함수가 FMMU 를 설정하고 포인터를 채운다

// 각 슬레이브의 입출력이 io_map 안의 어느 위치인지 SOEM 이 알려준다
struct AxisIo {
    const std::uint8_t* inputs;    // ec_slave[i].inputs
    std::uint8_t*       outputs;   // ec_slave[i].outputs
};

// 제어 루프에서는 그냥 메모리를 읽고 쓴다
void write_target_position(AxisIo& axis, std::int32_t pos) {
    put_i32_le(axis.outputs + kTargetPosOffset, pos);
}
```

제어 루프 코드에 통신이 안 보인다. 메모리를 읽고 쓰면 `ec_send_processdata()` 가 알아서 나른다. 이게 논리 주소와 FMMU가 주는 추상화다.

## 6. 부팅 절차 전체

주소 방식이 부팅 단계를 그대로 반영한다.

| 단계 | 주소 방식 | 하는 일 |
| --- | --- | --- |
| ① | 자동증가 | `BRD` 로 개수 세기, `APRD` 로 각 슬레이브 정보 읽기 |
| ② | 자동증가 | `APWR` 로 설정 주소 배정 (레지스터 0x0010) |
| ③ | 설정주소 | `FPWR` 로 각 슬레이브의 SM과 FMMU 설정 |
| ④ | 설정주소 | 메일박스로 CoE 설정, PDO 매핑 등 |
| ⑤ | 브로드캐스트 | `BWR` 로 전체 상태 전이 명령 |
| ⑥ | 논리주소 | `LRW` 로 프로세스 데이터 주기 통신 시작 |

모르는 상태(주소 없음)에서는 자동증가, 아는 상태(주소 배정됨)에서는 설정 주소, 전체에게는 브로드캐스트, 운전 중에는 논리 주소다.

SOEM의 `ec_config_init()` 이 ①②를, `ec_config_map()` 이 ③을, `ec_writestate()` 와 `ec_statecheck()` 가 ⑤를 한다.

## 7. 진단

| 증상 | 확인 |
| --- | --- |
| 슬레이브 개수가 예상과 다르다 | 케이블, 전원, BRD WKC 확인 |
| 특정 슬레이브가 응답 없음 | `FPRD` 로 개별 확인. 설정 주소가 제대로 써졌나 |
| 배선 순서를 바꿨더니 다르게 동작 | 정상이다. 자동증가는 물리 순서 기반이라 재설정이 필요하다 |
| 프로세스 데이터가 엉뚱한 슬레이브로 | FMMU 매핑 (06편) |
| WKC가 기대보다 작다 | 04편 |

슬레이브 순서를 바꾸면 다르게 동작한다는 것은 결함이 아니라 설계다. EtherCAT에서 슬레이브의 정체성은 물리적 위치에 있다.

그래서 배선도와 슬레이브 순서를 문서로 관리해야 한다. Vendor ID, Product Code, 시리얼 번호를 부팅 시 확인해서 예상한 구성과 다르면 거부하는 코드를 넣으면 사고를 막는다.

```cpp
// 부팅 시 구성 검증 — 배선이 바뀌었는지 확인
bool verify_topology(std::span<const ExpectedSlave> expected) {
    if (ec_slavecount != static_cast<int>(expected.size())) return false;
    for (int i = 1; i <= ec_slavecount; ++i) {
        if (ec_slave[i].eep_man != expected[i-1].vendor_id)   return false;
        if (ec_slave[i].eep_id  != expected[i-1].product_code) return false;
    }
    return true;
}
```

## 정리

- EtherCAT 슬레이브에는 출고 시 주소가 없고 네 가지 주소 방식이 부팅 단계를 따라간다
- 자동 증가는 위치 카운터가 슬레이브를 지날 때마다 +1 되고 0인 슬레이브가 처리한다. 부팅 초기 스캔과 주소 배정에 쓴다
- 설정 주소는 배정한 16비트 주소로 직접 지목한다. 레지스터 접근, 메일박스, 설정에 쓴다
- 브로드캐스트의 `BRD` 는 결과가 논리 OR라서 "전부 같은 상태인가" 를 프레임 하나로 확인할 수 있다. WKC가 곧 슬레이브 개수다
- 논리 주소가 제어 루프의 주력이다. 4 GB 가상 공간에 전체 프로세스 이미지를 배치하고 `LRW` 하나로 읽고 쓴다
- 6축에서 208 B가 148 B로 29% 줄고 슬레이브가 늘수록 격차가 커진다
- 마스터 코드에서 통신이 사라진다. IOmap 메모리만 읽고 쓰면 된다
- 부팅 순서가 주소 방식 순서와 같다: 자동증가, 설정주소, 브로드캐스트, 논리주소
- 슬레이브의 정체성은 물리적 위치다. 배선 순서를 바꾸면 재설정이 필요하고 이건 결함이 아니라 설계다
- 부팅 시 Vendor ID와 Product Code로 구성을 검증하면 배선 사고를 막는다
